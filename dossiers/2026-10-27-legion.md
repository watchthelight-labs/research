# The Legion 5 15IAX10 Hackintosh in late October 2026: what the public web knows about the Arrow Lake-HX stalls, NvGfx, MT7925 and macOS 26.7.2: Supersearch Research Dossier

- **Generated:** 2026-10-27 (every "checked" date in this document is this day unless a line says otherwise)
- **Mode:** Exhaustive (15 research agents, then an audit, a contradiction pass with independent re-verification, a timeline pass, a practitioner pass, four theme syntheses, a devil's advocate and a quality gate)
- **Quality gate:** PASS for use as a planning document (WARN on source diversity and search reach); scores in the methodology section
- **Sources included:** 229 in the sources table (337 unique URLs were read across the research reports)
- **S and A tier sources:** 108 in the sources table (about 170 of the 337 URLs after the audit's stricter regrade)
- **Subject machine:** Lenovo Legion 5 15IAX10 (Core Ultra 9 275HX, Intel iGPU 8086:7D67, RTX 5070 Laptop GB206, MediaTek MT7925, Realtek ALC257) on macOS Tahoe 26.7.1 (25G241) through OpenCore, running the project's own NvGfx, XeGfx, MtkWlan/MtkWlanNative and MtkBt drivers.

## Executive summary

The public web has no report that matches the project's I-116 stall. There are Linux reports on the same family of parts, mostly Arrow Lake-H and Meteor Lake rather than the 275HX die, where the GuC firmware acknowledges a TLB invalidation about 2.3 seconds late and some machines then freeze. Those freezes keep the kernel alive (SysRq works, the journal keeps writing) and the NMI watchdog never fires. The I-116 panic is different: one CPU never reaches the rendezvous and the other 23 do not answer even an NMI. The only confirmed root cause for the Linux late acknowledgements is stale CPU cache lines of firmware-written memory on the standalone media GT, fixed in a commit that reaches Linux 7.4, and XeGfx skips the media GT in every recorded boot. The `fwtable_write32` frame in the I-116 panic is most plausibly the GuC doorbell write, and Intel's own source marks that register's forcewake handling as a FIXME workaround for delays when the platform changes sleep state. That is a lead and not a diagnosis: in only one of four recorded panics is the panicking CPU in driver code, that CPU had also taken an interrupt and may be a waiter, and rivals that the public record cannot separate include a System Management Mode stall (the project's NVRAM trace writes every 250 ms and has been on in every guarded run) and the project's own power kext, which was loaded in every run.

The platform research found no firmware fix to wait for. Lenovo's S2CN26WW is the newest BIOS for this machine and only updated CSME. Intel's specification update (revision 024, October 2026) still lists erratum ARL037 (a core can hang entering or leaving C6 or deeper, with no machine check logged) as "Planned Fix" on the HX line, but Intel calls it synthetic, it hangs one core, and the panic needs a machine-wide stall. Newer microcode (0x121, 0x122) exists against the 0x11b this machine runs, with no public text tying it to the erratum. For I-118 (resets 15 to 40 seconds after OpenCore's ExitBootServices line, after two Linux probe sessions) nothing public matches: no one reports an Arrow Lake reset as opposed to a hang. The candidates are leftover state from the previous OS (microcode, GSP/WPR2, a Linux-armed watchdog, VT-d state), all supported by analogy only, and the log line "EXITBS" marks where OpenCore's log stops, not where the machine died.

On the graphics side, NullMoth's current release (2.6.2) carries the same driver as 2.5.5, and the project's 2.6.2 rebase is built but not booted (N-294). Independent evidence for the NVIDIA problems (drag stalls, HiDPI, HDR, Chrome flicker, MPS translation) is thinner than it looks and some of it is the project's own account. Several Intel Xe on macOS efforts are active (ArrowWhatever on the same die, zep245's Tiger Lake port, jwx29's fork, VedCloud's Meteor Lake notes); the only soak figure on this die is a self-reported 40 minutes, from a patched copy of the project's own shim. ArrowWhatever fixed a userptr unwire race that the project's code also contains, with a different failure signature. zep245 found NVRAM trace writes to be a hot-path cost, which has never been tested in XeGfx and is a switch away; if native NVRAM writes run in System Management Mode, that switch is also a test of the stall.

For macOS, 26.7.2 is build 25G332 (released 2026-10-26); 25G330 was the third release candidate, and the project's tracker and one public reply use the wrong number. The kernel collections of 25G332 can be rebuilt without installing anything, by applying Apple's own BXDIFF50 delta patches to the files already on the Mac, and the result verifies against hashes. A first ABI comparison shows unchanged class sizes and vtables with three small differences, so the native Wi-Fi front end's refusal on 25G332 looks like a gate decision more than a proven break. Bluetooth reports mix a probable stale byte pin with a card-state fault. Intel Macs end at Tahoe, so every point release is a recurring cost for kexts that depend on private layouts.

## Bottom line

- I-116 has no public twin. Rank the experiments by cost: one session at stock LegionCpuPower limits with the SMI count read, one run with the NVRAM trace off, passive per-CPU and TSC timing around the doorbell and forcewake waits so the missing CPU gets a name, machine-check banks after the next stall, and only then the waker by `gtawake` 2x2 with a stopping rule. Do not write that I-116 is "the 2.3 second cache bug", and do not use `tlbto_us=0`, which removes the panic string.
- Do not wait for a BIOS or microcode fix, and do not load newer microcode through OpenCore as a mitigation. None is published, and early loading over an older BIOS revision broke other Intel parts in 2026.
- For I-118, make the cold-versus-warm state a recorded column, record the microcode revision and the watchdog state before and after each Linux probe, and fully power off after Linux before testing macOS.
- Stay on 25G241 and prepare 25G332 offline: correct the "25G330" records, review the three ABI differences, explain why the live bluetoothd does not match the OTA record, and ask reporters for the Wi-Fi refusal reason.
- Treat the self-reported peer projects as claims. Port the userptr race fix as the project's own code, and do not log it as an I-116 attempt.
- Nothing in this dossier needs an outside post; anything on a public tracker is Bash's decision.

## Key insights

1. **Intel treats the doorbell write as an unfinished workaround.** The H2G doorbell (register 0x1901f0) is in a range that normally needs no forcewake, but Intel added GT forcewake for it because the write can be delayed when the platform enters or leaves a sleep state, and marked it FIXME pending an official workaround. A separate commit says the same about multicast steering registers. This is the best mechanism-level match for the I-116 frame, and it points below the driver. Sources: [6d46d09a0d7d](https://github.com/torvalds/linux/commit/6d46d09a0d7dd412c5b76f74f89fe4448ba2117e), [8fa1c7cd1fe9](https://github.com/torvalds/linux/commit/8fa1c7cd1fe9). Confidence: Medium (the link to I-116 is inference; the panic carries no register offset).
2. **The one root cause everyone cites is scoped to a GT that XeGfx does not start.** Wa_22016122933 concerns memory shared with the media GuC, XeGfx logs "Skipping GT1" in seven boots, and the supporting measurements come from Arrow Lake-H machines. Its own reporter saw a silent death with the fix applied. Sources: [xe commit d5b0bf3f37f1](https://github.com/torvalds/linux/commit/d5b0bf3f37f152583a884c696cf6caa152aa7ed5), [xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678). Confidence: High on the scope, Medium on the inference that it cannot be ours.
3. **Same-silicon Linux freezes leave the kernel alive; I-116 does not.** Reports on 7D67 and 7DD1 end with a live kernel or a silent power-off with nothing captured, and none carries a per-CPU state comparable to the I-116 panic. Sources: [xe 9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168), [i915 16937](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/16937). Confidence: Medium-High.
4. **A GT hold tests a different failure class than the one Intel is fixing.** The Tiger Lake macOS port and the FreeBSD maintainer both stopped hangs by keeping the GT awake, but both are other silicon and neither had a controlled A/B, and the owner of xe 8678 held forcewake on Arrow Lake while the late acknowledgements continued. A hold is a test for a CPU-side or sleep-state class (that I-116 is in it is assumed, not shown), and a negative result on one must not be read across. Sources: [drm-kmod 457](https://github.com/freebsd/drm-kmod/issues/457), [xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678). Confidence: Medium.
5. **The panic is a late detector and the stall length is unknown.** The rendezvous spin is bounded at about 2.0 seconds, so "2 s" is a timeout and not a measurement; the 27 s figure in one run record contradicts the saved progress file; the panicking CPU is a waiter in most runs. Naming the missing CPU is the most valuable extra datum, and the SMI count (MSR 0x34) separates an SMM stall from an uncore hang. Sources: [xnu mp.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c), [LKML on stuck MMIO](https://lkml.iu.edu/2601.1/13174.html). Confidence: High on the arithmetic.
6. **Shim semantics are a live candidate beside silicon.** FreeBSD found three LinuxKPI gaps behind GuC scheduling failures on Meteor Lake, and the same silicon ran a 40-minute soak under a patched copy of this project's own shim (self-reported, two days old, inside the project's own spread of times to stall). The stand-ins for `in_atomic`, `irqs_disabled` and `rcu_preempt_depth` decide whether a full H2G buffer sleeps or spins. Sources: [freebsd-src 4f2f26fb1e8a](https://github.com/freebsd/freebsd-src/commit/4f2f26fb1e8a), [ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever). Confidence: Low.
7. **ARL037 fits the first phase of the panic and not the second.** One core hanging with no machine check matches the single missing CPU; it does not explain 23 CPUs ignoring an NMI, Intel calls it synthetic, and four freezes happened on Linux with a C-state limit of 2 and display power states off. Sources: [Intel 834774 rev 024](https://cdrdv2-public.intel.com/834774/834774_024.pdf), [xe 9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168). Confidence: Low.
8. **No firmware fix is known, so there is none to wait for.** S2CN26WW is the newest BIOS (checked), microcode 0x121 and 0x122 have no public mapping to ARL037 (an absence claim from one search pass), and loading microcode early over an older BIOS broke Meteor Lake machines in August 2026. Sources: [Lenovo readme](https://download.lenovo.com/consumer/mobiles/s2cn26ww.txt), [microcode releases](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/releases), [microcode issue 112](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/issues/112). Confidence: Medium (the BIOS fact is High; the absence of a fix is one search pass).
9. **For I-118 the unrecorded variable is cold versus warm.** Intel's triager asks for it on the one 7D67 probe-failure thread, NVIDIA's WPR2 reports hinge on it, and the project's failing and passing boots differ in that column. Every candidate (microcode persistence, WPR2, a Linux watchdog, VT-d) is an analogy. Sources: [i915 16052](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/16052), [open-gpu-kernel-modules 1353](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1353). Confidence: Medium.
10. **The Intel Xe peers fixed glue-code bugs, which are cheap to close.** The userptr unwire race is a lock gap that exists in XeGfx and does not match the I-116 signature. The NVRAM trace cost is a hot-path problem, and because native NVRAM writes on EDK2-derived firmware normally go through System Management Mode (unverified for this BIOS), the trace is also a candidate cause of the stall, and more than a tidy-up. Sources: [ArrowWhatever userptr note](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/userptr-panic.md), [zep245 design notes](https://github.com/zep245/IrisXe-macos-driver/blob/main/DESIGN.md). Confidence: Medium.
11. **Independent evidence on the NVIDIA problems is thin, and some of it is ours.** The HDR trace and the 12-byte HiDPI finding came from the project's own account; the Chrome Graphite cure and the MPS failures have several independent reporters. The 615.71.10 and 615.78.08 source diffs show no platform logic change, and the project's one GSP control already lifts the 50 W default to 115 W. Sources: [nullmoth 341](https://github.com/nullmoth/nvidia-macos-driver/issues/341), [NVIDIA compare](https://github.com/NVIDIA/open-gpu-kernel-modules/compare/615.71.09...615.78.08). Confidence: Medium.
12. **The 26.7.2 Wi-Fi break is a gate decision first, and the gate is a safety gate.** The front end refuses on the xnu tag before it looks at sizes, and the offline comparison shows unchanged sizes and vtables with three unreviewed function differences, one plausibly relevant. No 25G332 boot of the project's kexts has happened, so this stays inference. Sources: [MtkNativeAbi.hpp](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi-native/blob/main/src/MtkNativeAbi.hpp), [appledb 25G332](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G332.json). Confidence: Medium.
13. **Tahoe is the last Intel macOS, so each point release is a recurring cost for private-layout kexts.** The newest MT7925 competitor shares the per-build pin. Automating the offline kernel-collection route is worth more than any single 25G332 fix. Sources: [Apple macOS page](https://www.apple.com/os/macos/), [OCLP 1183](https://github.com/dortania/OpenCore-Legacy-Patcher/issues/1183). Confidence: Medium.
14. **Arrow Lake Hackintosh practice converges on VT-d off, a DMAR drop and a type-0 MADT, and this config differs in two quirk choices.** Two other 275HX EFIs (not independent of one another's guide lineage) run SetupVirtualMap on without ForceExitBootServices, while this config does the opposite and keeps DMAR. None of those projects reports I-118-style resets, and this machine's normal boots pass, so a quirk A/B is a hypothesis. Sources: [1401 issue 58](https://github.com/nullmoth/1401/issues/58), [ASUS FX608LP EFI](https://github.com/CENSEDAXIS20025/ASUS-FX608LP-Hackintosh-Multiboot). Confidence: Medium.

## Theme 1: I-116, what Linux i915 and xe, FreeBSD drm-kmod and other ports know about GuC CT, forcewake, TLB-invalidation and free-worker stalls on Meteor Lake and Arrow Lake

### 1.1 The best-supported mechanisms are two different late-ack effects, and neither is shown to be our whole-machine stall

Upstream has published evidence for two ways a GuC acknowledgement arrives late on Meteor Lake and Arrow Lake. The first is a stale CPU cache read: the GuC answers in time, but the CPU keeps reading an old empty line of the G2H buffer. Intel's xe fix [d5b0bf3f37f1](https://github.com/torvalds/linux/commit/d5b0bf3f37f1) (Wa_22016122933) took one reporter from 20 to 60 stalls a day to zero in six weeks over more than ten million invalidations ([xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678)). The second is a platform sleep-state delay on a write that forcewake does not cover: [6d46d09a0d7d](https://github.com/torvalds/linux/commit/6d46d09a0d7d) says there "could be some delays when platform is entering/exiting some higher level platform sleep states" for the H2G doorbell.

Our signature differs from both. I-116 is a whole-machine stall, then an XNU rendezvous panic in which 23 of 24 CPUs answered and none took the NMI. The XeGfx log ring held no i915 message after GuC load (no CT timeout), and in N-288 the GPU interrupt counters kept moving with every interrupt handled. The closest local match to the second mechanism is N-287, where the panic CPU sat in `fwtable_write32` under `intel_guc_ct_send` during an execbuffer ioctl, the doorbell path. This is inference: no public report measures that write stalling, so the link is a hypothesis.

The cache mechanism is excluded unless our shim has a GT0 analogue (1.4). A platform stall that no driver timer catches cannot be excluded, and 1.6 shows why the evidence leans that way.

**Confidence:** Medium (checked 2026-10-27) that these are the two documented mechanisms; Low that either explains I-116.

### 1.2 I-116 is a two-phase XNU panic, and its real stall length is unknown

The panic strings read `mp_rv_action() entry: 23 of 24 responses`, then `mp_kdp_enter() ... expected 24 acks but received 1` after 1536000000 ticks. XNU's [rendezvous code](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c) uses a spin timeout of four times the lock timeout, and the NMI ack wait is half a second; at 3.072 GHz that is 2.0 s and 0.5 s. I computed (cur - start) from the N-287, N-288 and N-290 panic strings: about 6.144e9 ticks, exactly 2.0 s. The panic therefore fires at the normal timeout after the rendezvous began, not after a long stall, and how long the machine had been stuck is not in the data.

"23 of 24" means one CPU never entered the rendezvous (its id is not printed). Phase two, in which none of the other CPUs acknowledged an NMI although about 22 had entered, needs more than one stuck CPU: an SMM or SMI episode, a fabric or memory stall, or CPUs unable to take NMIs. This is inference and Unverified.

The panic CPU is a waiter, not the culprit. N-287 (about 45 s after WindowServer started): in or below `fwtable_write32 + 0xfa`, called from `intel_guc_ct_send`. N-288 (about 40 s): idle in `processor_idle`. N-289 (15 to 20 s): `pmap_remove_range` from the free worker (`IOBufferMemoryDescriptor::free <- xg_vm_x_release <- __i915_gem_free_objects`). N-290 (88 min, during `diskutil apfs resizeContainer`): storagekitd in `nx_resize`. One puzzle: i915 runs `fwtable_write32` under `spin_lock_irqsave`, and the N-289 README says the shim's `spinlock_enter` masks interrupts, yet CPU 3 took an IPI there. Either the interrupted address is a return after the unlock or the mask is not what we think; the `irqoff_check` switch tests this.

Two local record problems need fixing before publication. The N-287 README claims a 27 s guard-loop gap and that the unified log stops at 11:19:06, but the saved `N-287/guard/ws-progress.txt` has lines about every 5 s through 11:19:38 with IOPresentment counts still rising, so any "27 s stall" in the aspect reports is softened here. And N-290 ran 0.0.43 with a 20 ms interrupts-off watchdog and survived 88 minutes; the wakeup may make I-116 rarer, which is not proven.

**Confidence:** High (checked 2026-10-27) on the 2.0 s arithmetic from the saved panic strings; Unverified on the true stall length and the missing CPU.

### 1.3 Intel marks the doorbell as a FIXME workaround for sleep-state delays and says the pcode half is separate

The doorbell is register 0x1901f0 (GEN11_GUC_HOST_INTERRUPT), written by `intel_guc_notify` under the CT buffer's `spin_lock_irqsave`. [6d46d09a0d7d](https://github.com/torvalds/linux/commit/6d46d09a0d7d) (authored 2024-01-19, committed 2024-01-24, v6.9) added `GEN_FW_RANGE(0x1901f0, 0x1901f3, FORCEWAKE_GT) /* FIXME: WA to wake GT while triggering H2G */`. Its text says the register sits in the sgunit and "is not affected by forcewakes", and that "this will have an official WA soon". The accurate wording is "a FIXME workaround takes GT forcewake for that offset", not "the doorbell needs forcewake". Our drm-kmod base [c16de0f](https://github.com/freebsd/drm-kmod/commit/c16de0f9fa84) has the range; xe's `xe_guc_notify()` in [xe_guc.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/xe/xe_guc.c) is a plain MMIO write without it.

The sister commit [8fa1c7cd1fe9](https://github.com/torvalds/linux/commit/8fa1c7cd1fe9) (GT forcewake during MCR steering) cites the same cause and says "an upcoming pcode firmware update will also be necessary to provide the other half of this workaround". A pcode half implies a BIOS or IFWI dependency no kext can supply, which fits [Red Hat bug 2463170](https://bugzilla.redhat.com/show_bug.cgi?id=2463170) (reported fixed by a kernel update plus a Lenovo BIOS PCODE update).

`fwtable_write32` takes `uncore->lock`, calls `__force_wake_auto`, and each ack wait is 50 ms per pass with fallback passes. By my arithmetic a worst case exceeds one second (inference), enough to keep other CPUs waiting on that lock. This machine has BIOS S2CN26WW and microcode 0x11b; 0x121 and 0x122 exist, but no release note ties either to this symptom.

**Confidence:** High (checked 2026-10-27) that the commits say this; Medium that the pcode dependency applies to this laptop.

### 1.4 Wa_22016122933 is real on the media GT and probably does not apply because XeGfx skips GT1

[d5b0bf3f37f1](https://github.com/torvalds/linux/commit/d5b0bf3f37f1) (committed 2026-09-24, merged via drm-next on 2026-10-24, queued for 7.4, not in v7.3) covers the standalone media GT, media version 13.00, on Meteor Lake and Arrow Lake. Memory shared between the CPU and the media GT's GuC (CT buffers, log, ADS, SLPC) must not be CPU-cached, or the CPU reads a stale empty CTB until the line is evicted and the 2.25 s fence timeout fires first. A coherent WB|COH_2WAY mapping did not help (2290 ms); a CPU-WC variant works; swapping in `XE_BO_FLAG_FORCE_WC` naively flips the GGTT side to WB and stalls return ([xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678)). A follow-up patch on the [intel-xe list](https://lore.kernel.org/intel-xe/20261003222145.67240-1-navonjohnlukose@gmail.com/) (403 on fetch, described from the corpus) says uncached-only regresses probe to about 3.1 s and WC fixes it. i915 has carried the workaround since [a161b6dba6e0](https://github.com/torvalds/linux/commit/a161b6dba6e0) (v6.5-rc1), keyed on media version 13.0 and `GT_MEDIA`.

The XeGfx log reads `Skipping GT1 (Standalone Media GT) - MEI driver not available on FreeBSD`, matching drm-kmod [PR 418](https://github.com/freebsd/drm-kmod/pull/418). The workaround's scope is therefore absent from our run, and "I-116 is the 2.3 s cache bug" must not be written anywhere. Even with the fix, media-GT "not started" timeouts persist at about one per 100 h.

C9 in the contradiction file is a Low-confidence analogue on GT0: if the shim maps GuC shared pages cacheable while the GGTT side is snooped differently, a stale-line effect is conceivable. Nothing tests that. Reading how `xg_vm.c` maps CT pages and which PAT the GGTT entries use would settle it without a boot; the [XeGfx VM notes](https://github.com/watchthelight-labs/XeGfx/blob/main/docs/xg_vm.md) say a page run's kernel mapping is write-back.

**Confidence:** High (checked 2026-10-27) for the workaround's media-GT scope; Contradicted as an explanation of I-116; Low for a GT0 shim analogue.

### 1.5 The xe 8678 owner's forcewake hold did not stop the ack delay, and one machine died silently even with the workaround

The cached notes on [xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678) hold the most direct A/B on Arrow Lake. Note 1 (2026-07-30): forcewake held across the whole GT, GT C6 residency delta zero, still nine timeouts. A 250 ms doorbell re-kick shortened most acks to 15 to 276 ms, but severe episodes ignored 8 to 9 consecutive doorbells (worst 5996 ms); the owner first read that as GuC-side, then the list confirmed the stale-cache cause (note 15). So "a forcewake or RC6 hold stops the stall" is Contradicted for the late-ack class: late acks and a CPU-side blocked doorbell write are two separate mechanisms.

Note 26 says the series "would not have prevented" a GT0 wedge. Note 28 (2026-09-19) reports the owner's own 7d51 machine locking completely on 2026-09-16 on a kernel with the workaround, leaving no log line; the NMI watchdog and pstore captured nothing. Note 30 speculates (tier B) that a hang in a GPU power or fabric handshake "can take the whole package down". Other Arrow Lake H machines with backports ran clean. This is the closest public analogue to our silent phase, and it is one report without a root cause.

**Confidence:** High (checked 2026-10-27) on what the notes say; Medium that they transfer to 7D67.

### 1.6 Linux freezes on this silicon leave the kernel alive and ours does not, so the nearest analogues are few

[xe 9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168) (device 7d67, a 285HX mini PC) shows freezes with a live kernel: SysRq-S works, `nmi_watchdog=panic` never fires, the journal keeps writing, and a TLB timeout precedes the freeze by minutes to hours. A 2026-10-27 comment reports DC, PSR, FBC, panel replay and DMC wakelocks off plus `intel_idle.max_cstate=2` do not help. That is a different class from N-290, where the CPUs go silent. [i915 16937](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/16937) (ARL-P) is a hard hang with a silent NMI watchdog and about 1000 DC transitions a minute before death, not cured by PSR, FBC, `max_cstate=1` or removing the NVIDIA card. [i915 13926](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/13926) has forcewake and TLB timeouts with one CPU stuck in VT-d `qi_submit_sync`. No report matches 23 of 24 CPUs plus NMI silence on 7D67 in any operating system.

For the silent phase the best public statement is Gleixner's on another platform: a machine can stall on outstanding MMIO transactions "w/o further notice" and "the NMI is just a red herring" ([LKML, 2026-01-13](https://lkml.iu.edu/2601.1/13174.html)). That fits a CPU parked in an uncore write (N-287) and silent peers, but it is a model, not a measurement. Gleixner's text concerns HPET clocksource time failing to propagate after a hung PCI config read, so the remark about the NMI describes that path and does not transfer as a rule. The N-287 panic CPU was also running interrupt code (`cpu_signal_handler` sits above the `fwtable_write32` frame in the saved panic string), so it may have been a waiter that happened to be in driver code. The same silicon and macOS build did a 40-minute soak with zero stalls under a patched copy of this project's own XeGfx shim ([ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever), tier B, self-reported, created 2026-10-25), while N-290 died at 88 minutes under heavy I/O, so the trigger is setup-specific.

**Confidence:** Medium (checked 2026-10-27) that the silent phase has no direct public analogue; Low on any specific cause.

### 1.7 TLB invalidation has an MMIO fallback, but turning off the GuC path is not a one-flag test

`intel_gt_invalidate_tlb_full` in [intel_tlb.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/i915/gt/intel_tlb.c) is gated by wedged state, seqno coalescing and `with_intel_gt_pm_if_awake`, so not every free sends an H2G ("every free" claims are overstated). It takes the GuC path only if `HAS_GUC_TLB_INVALIDATION` and the GuC is ready, otherwise `mmio_invalidate_full`, which takes `FORCEWAKE_ALL` and the MCR lock and waits 100 us then 4 ms per engine. The GuC path ([intel_guc_submission.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/i915/gt/uc/intel_guc_submission.c)) sends through `intel_guc_send_busy_loop` and waits about 2 s before logging "TLB invalidation response timed out".

An aspect report called clearing `has_guc_tlb_invalidation` a one-flag experiment. That is wrong. [2d6e2b10a773](https://github.com/torvalds/linux/commit/2d6e2b10a773) says Meteor Lake "is presently the only platform that requires it for any purpose", and [af58ee227662](https://github.com/torvalds/linux/commit/af58ee227662) says GuC-based GGTT invalidation is incompatible with MMIO invalidation. In [intel_ggtt.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/i915/gt/intel_ggtt.c), `guc_ggtt_invalidate` sends through the CT per GT, a second H2G source beside the free path. Clearing the flag could leave GGTT and PPGTT paths inconsistent. This is a Medium-confidence reading of commit text and source, untested.

N-289 puts the free worker's `pmap_remove_range`, an XNU TLB shootdown, under the panic CPU. A shootdown is an IPI wait on every CPU, so one CPU stuck in an uncore write makes the next shootdown stall the rest (inference).

**Confidence:** Medium (checked 2026-10-27), from source and commit text read directly; fallback safety on 7D67 untested.

### 1.8 The free worker's `cond_resched` fixes are old latency work and nothing is specific to Meteor Lake or Arrow Lake

The relevant changes are generic: [deeee411a975](https://github.com/torvalds/linux/commit/deeee411a975) (2020, per-object `cond_resched` in `__i915_gem_free_objects`) and the 2021 series that flushes TLBs before releasing backing store ([7938d61591d3](https://github.com/torvalds/linux/commit/7938d61591d3) and neighbours), which made the free worker the main invalidation producer. The Tiger Lake port on XNU ([IrisXe-macos-driver](https://github.com/zep245/IrisXe-macos-driver), tier B) had a `preemption_level -1` panic from `cond_resched` (`ggtt_pin -> shmem_get_pages -> shmem_sg_alloc_table -> cond_resched -> sched_relinquish -> thread_block`), traced to an earlier lock imbalance and cured by turning off a per-CPU curthread cache. That points at the shim's critical-section accounting, not at the free worker. For us the N-289 panic CPU was already inside the shootdown, so `cond_resched` is not a cure; limiting how much one free pass does is a smaller experiment than touching the TLB path.

**Confidence:** Medium (checked 2026-10-27) that no ARL-specific free-worker fix exists; Low that throttling would change I-116.

### 1.9 GuC, firmware, DUAL_QUEUE_WA and render power gating: what our base already has

GuC submission is the Linux default on Meteor Lake and Arrow Lake, and xe dropped `force_execlist` ([b623bd790db0](https://github.com/torvalds/linux/commit/b623bd790db0)). XeGfx's [HOW-IT-WORKS](https://github.com/watchthelight-labs/XeGfx/blob/main/docs/HOW-IT-WORKS.md) says that drm-kmod disables the GuC by default, that these parts have no execlist submission (the no-GuC path returns -EIO and the GT is declared wedged), and that XeGfx sets `enable_guc=3`. "Switch to execlists" is therefore not an available A/B on 7D67; whether a HuC-only `enable_guc=2` mode works is unsettled. FreeBSD defaults GuC off because of shutdown and reboot freezes ([drm-kmod 399](https://github.com/freebsd/drm-kmod/issues/399)).

I checked the base [c16de0f](https://github.com/freebsd/drm-kmod/commit/c16de0f9fa84) (2026-10-08, "Reduce diff with Linux 6.14"): DUAL_QUEUE_WA is set for graphics IP 12.70 or newer with CCS, as in [ff868667a4f9](https://github.com/torvalds/linux/commit/ff868667a4f9), and it is engine-level, not whole-machine. Render power gating stays excluded for IP 12.70 to 12.74 in its `intel_rc6.c`, following [25e7976db86b](https://github.com/torvalds/linux/commit/25e7976db86b) (forcewake ack timeouts in CI); upstream limited that exclusion to selftests in [0a4ae87706c6](https://github.com/torvalds/linux/commit/0a4ae87706c6) (v6.16). So we run the conservative setting upstream later dropped, with RC6 and media power gating on.

GuC 70.53.0 is what linux-firmware ships and our log shows. 70.74.0 is in drm-firmware and runs in Intel CI on Meteor Lake, but 70.72.1 behaved like 70.53.0 in xe 8678, so a firmware swap is low yield.

**Confidence:** High (checked 2026-10-27) for DUAL_QUEUE_WA and render-PG state, read from source; Medium for the firmware conclusion.

### 1.10 FreeBSD fixed shim-semantics bugs that produced GuC scheduling failures

[drm-kmod 457](https://github.com/freebsd/drm-kmod/issues/457#issuecomment-5470680199) (2026-08-30) diagnosed a GuC "Bad context sched_state" hang that `sleep 3000 < /sys/kernel/debug/dri/0/i915_forcewake_user` cured. Two causes were named: LinuxKPI runs the handler in an ithread, not a hardirq filter, so RC6 entry and exit happens during the delay and the `GFX_MSTR_IRQ` read returns invalid state; and the preemptible handler makes the masked window long. This is a correlation without a controlled A/B, and a later `cancel_delayed_work_sync` fix was called cleaner.

The fixes are small and checkable. FreeBSD [79e290d96786](https://github.com/freebsd/freebsd-src/commit/79e290d96786) (2026-09-13) corrected an inverted `cancel_delayed_work_sync()` return value, found while debugging GuC scheduling failures. [0d022baa047a](https://github.com/freebsd/freebsd-src/commit/0d022baa047a) runs irq_work callbacks under RCU. [4f2f26fb1e8a](https://github.com/freebsd/freebsd-src/commit/4f2f26fb1e8a) implements `irqs_disabled` and names `intel_guc_send_busy_loop` as a user, which matters because [intel_guc.h](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/i915/gt/uc/intel_guc.h) picks sleeping or an unbounded `cpu_relax()` retry from `in_atomic()`, `irqs_disabled()` and `rcu_preempt_depth()`. OpenBSD [bd7ea2868af8](https://github.com/openbsd/src/commit/bd7ea2868af8) polls CT receive while waiting. FreeBSD agreeing with Linux is not a second opinion; it is the same code.

The Tiger Lake port on XNU adds a ladder ([`nmx_i915_awake.c`](https://github.com/zep245/IrisXe-macos-driver)): a GT power reference alone still froze, adding `intel_uncore_forcewake_get(FORCEWAKE_ALL)` was clean, and the freeze needed paced 60 fps frames, never back-to-back submission. One machine, no controlled A/B. XeGfx 0.0.44 and 0.0.45 already carry matching switches (`gtawake=1`, `gtawake=2`, `irqoff_check=0`), built but not booted ([XeGfx](https://github.com/watchthelight-labs/XeGfx)).

**Confidence:** Medium (checked 2026-10-27); commits verified, effect on I-116 is inference.

### 1.11 Platform errata and microcode are weak fits

Intel's [specification update 834774 rev 024](https://cdrdv2-public.intel.com/834774/834774_024.pdf) lists ARL037, "A Core May Hang When Entering or Exiting C6 or Deeper Sleep States", as Planned Fix on HX (Fixed on H, N/A on U; an earlier aspect report had the columns wrong). Per Intel it is synthetic-only and hangs one core, not 23 of 24, so it is a weak fit. [i915 16052](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/16052) (7d67 probe-time all-ones MMIO reads, Intel text marked LLM-assisted) is a power-sequencing race with a request for cold versus warm results; the contradiction file says to drop it from the TLB-freeze list because it relates to I-118. Microcode and BIOS are variables we have not moved, and moving them needs Bash's OK.

**Confidence:** Low (checked 2026-10-27) that errata explain I-116; High on the stated erratum status.

### Theme 1 key insights

1. Holds test one failure class and not the other. The Tiger Lake port on XNU was cured only when it held forcewake on all domains ([zep245](https://github.com/zep245/IrisXe-macos-driver)) and FreeBSD's `forcewake_user` workaround stopped a GuC scheduling hang ([drm-kmod 457](https://github.com/freebsd/drm-kmod/issues/457#issuecomment-5470680199)), yet the [xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678) owner held forcewake and the ack stall went on. A hold is a test for the whole-system class (ours is assumed, not shown), not the late-ack class, and a negative result on one must not be read across. The positive evidence comes from two ports on other silicon (Tiger Lake, Meteor Lake) and the one hold on Arrow Lake failed. Confidence: Low to Medium.
2. A platform cause is not excluded, though no newer BIOS or microcode path exists on macOS. Intel's two FIXME commits ([6d46d09a0d7d](https://github.com/torvalds/linux/commit/6d46d09a0d7d), [8fa1c7cd1fe9](https://github.com/torvalds/linux/commit/8fa1c7cd1fe9)) call themselves half a workaround awaiting pcode, and a silent platform death with the cache workaround applied ([xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678), note 28) suggests a path no kernel patch reaches. BIOS and microcode are variables this project has never moved, and both statements here are absence claims from one search pass. Confidence: Low to Medium.
3. Our observables do not exclude a stalled MMIO transaction, and it fits them better than an ack delay, but it is a model. The N-287 panic CPU sits in an uncore write path yet had also taken an IPI, so it may be a waiter; the panic CPUs of N-288 to N-290 were in idle, in `pmap_remove_range` and in APFS reads, so only one of four runs shows the driver; the silent CPU is unnamed. System Management Mode (an SMI stops every thread while the TSC runs on), an EC or firmware event, and a failed deep-idle wake are rivals that the data do not separate. The 2.0 s rendezvous timeout and the NMI silence resemble [Gleixner's description](https://lkml.iu.edu/2601.1/13174.html), while every upstream mitigation targets ack delays. TSC deltas around the doorbell and forcewake waits are the discriminating measurement, together with the SMI count (MSR 0x34). Confidence: Low (inference).
4. A shim-semantics cause is a live candidate, not a favourite. FreeBSD found three LinuxKPI gaps behind GuC scheduling failures ([79e290d96786](https://github.com/freebsd/freebsd-src/commit/79e290d96786), [4f2f26fb1e8a](https://github.com/freebsd/freebsd-src/commit/4f2f26fb1e8a)), and the same silicon ran a 40-minute soak clean under a patched copy of our own XeGfx shim ([ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever), self-reported and not independent of our code; a 40-minute run also sits inside our own spread of 900 s passes and an 88-minute death). Our `in_atomic`, `irqs_disabled` and `rcu_preempt_depth` stand-ins steer `intel_guc_send_busy_loop` between sleeping and spinning. Confidence: Low. Its passive checks (reading the stand-ins) come before any boot test.
5. Heavy I/O and the free worker meet at TLB shootdowns. The free worker became the main invalidation producer in 2021 ([7938d61591d3](https://github.com/torvalds/linux/commit/7938d61591d3)), N-289 shows it inside `pmap_remove_range`, and N-290 died during an APFS resize. A CPU stuck with interrupts masked makes every other CPU's shootdown wait, so I/O load may raise the chance of a wedge without being its cause. Confidence: Low (inference).

## Theme 2: The Arrow Lake-HX platform under the stalls and the resets

### 2.1 ARL037 is the only published HX erratum shaped like the first half of I-116, and it fails three tests

Intel's Core Ultra (Series 2) Specification Update (document 834774, revision 024) lists ARL037: a core can hang entering or leaving C6 or deeper, no machine check is logged, Intel saw it only in synthetic conditions, and a BIOS workaround is possible. The status row is Planned Fix for S, S 6+8 and HX/HX Plus, N/A for U, Fixed for H ([Intel 834774 rev 024](https://cdrdv2-public.intel.com/834774/834774_024.pdf)). It was added in revision 008 (May 2025) and updated in revision 012 (October 2025) (same PDF). So on our 275HX it is acknowledged, unfixed in silicon as of October 2026, and left to firmware. Aspect 2 had the column mapping reversed (fixed on HX); the spec text and Aspect 5 are right, and verification pass agrees.

It fits phase 1 of I-116: the panic reports `23 of 24 responses`, so exactly one of 24 logical CPUs never answered the debugger rendezvous ([xnu mp.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c); panic record in `evidence/native/N-290/README.md`). It fails on three counts. Intel says synthetic only, and our stalls come within minutes of a WindowServer session. In phase 2 none of the other 23 CPUs acknowledge the NMI, and ARL037 says nothing about healthy cores going silent (this is inference: a hung core might stall IPI delivery, but no source says so). And the waker evidence is weak: the 20 ms waker thread in XeGfx 0.0.43 coincided with one surviving session, but 0.0.43 also added spinlock and interrupt instrumentation, and the direction of the waker's effect on idle is unknown: this text reasons that a timer waking a core 50 times a second adds C6 transitions, while the N-290 README says it keeps cores out of deep idle, and neither has been measured. It is not a ranking input.

The other errata fit worse. ARL042 (package C6 exit hang, Geyserville) is Fixed on HX. ARL068 (PCIe Gen5 L1 substate exit, with `THREE STRIKE` and `INTERNAL TIMER` machine checks) is No Fix on HX, but needs a Gen5 link in L1 substates and logs an MCE; our NVMe link is Gen4, Linux logs `FADT indicates ASPM is unsupported` here (`evidence/native/N-274/hw/dmesg.txt`), and I-116 shows no MCE. ARL004 is VMD-only, ARL031/041/043/049 are H-only ([same PDF](https://cdrdv2-public.intel.com/834774/834774_024.pdf)). The Meteor Lake RC6 exit errata MTL037/042 cited by Aspect 4 were not re-fetched, and their relevance to our iGPU rests on shared Xe lineage (inference). The Wa_22016122933 media-GT workaround cannot be the cause because XeGfx never touches GT1 (verification pass). Intel's text names no die-to-die, ring or fabric erratum for HX.

**Confidence:** Low (best candidate for phase 1 only; synthetic-only wording and phase 2 count against it).

### 2.2 The Linux Xe reports are a different failure class, and their evidence against C-states is weaker than reported

[i915 16052](https://gitlab.freedesktop.org/drm/i915/kernel/-/issues/16052) is an all-ones MMIO read at probe on a 7d67 iGPU (our device ID). Intel's triager called it a hardware/firmware power-sequencing race, noted LLM-assisted triage, asked for cold versus warm, dGPU disabled and another BIOS, and set the issue to close on 2026-10-27 without data. In xe [9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/9168) the freezes keep the kernel alive, and in [8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/8678) holding forcewake did not stop the acknowledgement stall. Verification pass therefore treats them as unlike our whole-machine stall with an xnu panic, and I agree.

The claim that 9168 rules out C-states does not hold. Its reporters are ARL-H, where ARL037 is Fixed, so they cannot test it, and the reporter who used `intel_idle.max_cstate=2` with DC, PSR and FBC off still saw four power-offs on 2026-10-27, but 2.3 shows that setting leaves a core C6-class state on. What the reports show is a shared power-sequencing weakness in the 7d67 and 7dd1 families, not a CPU idle verdict. One data point from our probe: the 47-minute Linux 7.0 capture, which had no stall, logs `Invalid mmio detected during user access` from i915, three seconds after nouveau re-enabled the dGPU's HDA controller ([dmesg](evidence/native/N-274/hw/dmesg.txt); message source [intel_uncore.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/i915/intel_uncore.c)). One occurrence is not evidence, but it sits beside a dGPU power event, which is what Intel asked about (inference).

**Confidence:** Medium (issue text verified 2026-10-27; mapping to I-116 is inference).

### 2.3 `max_cstate=2` does not exclude core C6, and macOS gives us no C-state counters

Linux has no Arrow Lake table in `intel_idle`; the driver falls back to ACPI `_CST` and honours `intel_idle.max_cstate` there ([intel_idle.c](https://github.com/torvalds/linux/blob/master/drivers/idle/intel_idle.c)). An Arrow Lake report shows `_CST` MWAIT hints 0x0, 0x21 and 0x60 ([Unraid](https://forums.unraid.net/topic/197400-intel_idle-not-registering-native-c-states-on-intel-core-ultra-200-series-arrow-lake-model-0xc6/)); Meteor Lake's table uses 0x20 for C6 and 0x60 for C10 (same intel_idle.c), so 0x21 is a core-C6-class state and `max_cstate=2` keeps it (inference). Aspect 4 and Aspect 15 said Arrow Lake does not use intel_idle and the knob is not the lever; the source shows the fallback, so I overrule them.

On macOS, XCPM runs under a Comet Lake CPUID spoof (`Cpuid1Data` 55060A00 in our OpenCore config), and LegionCpuProbe publishes no residency counters. Package C2 needs all cores in C6 or deeper and graphics in RC6 ([Intel datasheet, H/U parts](https://edc.intel.com/content/www/us/en/design/products-and-solutions/processors-and-chipsets/core-ultra-200h-and-200u-series-processors-datasheet-volume-1-of-2/package-c-states/)). The registers worth reading are the common ones: core 0x3FC to 0x3FE, package 0x3F8 to 0x3FA, 0x60D and 0x630 to 0x632, 0xE2 (C-state config, CFG lock), 0x34 (SMI count) and the MCi_STATUS banks from 0x401 ([Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)). Whether Arrow Lake implements each address is unverified.

**Confidence:** Medium (kernel source read directly; the 0x21 mapping and the MSR list on this die are inference).

### 2.4 Microcode 0x11b and BIOS S2CN26WW are not the newest, but nothing ties newer ones to ARL037

We run microcode 0x11b (macOS reports 283; Linux logs `Current revision: 0x0000011b` with no update line, [N-274 dmesg](evidence/native/N-274/hw/dmesg.txt)). Intel shipped 0x121 on 2026-05-12 ([release](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/releases/tag/microcode-20260512)) and 0x122 on 2026-08-11 ([release](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/releases/tag/microcode-20260811)) for the 06-c6-02 B0 part, after 0x11a (2025-11-11) and 0x11b (2026-02-10). Aspect 5 said three newer revisions; only two exist. The notes say only "Update for functional issues" and cite the same spec update, so "0x121 fixes ARL037" is a guess. Newer microcode over old firmware has broken boot on other parts ([issue 112](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/issues/112), [113](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/issues/113)).

Lenovo's S2CN26WW (readme 2026-03-24, catalog 2026-05-06) is the newest BIOS for 83F0 and changes only "Update Intel CSME", EC untouched ([readme](https://download.lenovo.com/consumer/mobiles/s2cn26ww.txt)); S2CN27WW returns 404 ([probe](https://download.lenovo.com/consumer/mobiles/s2cn27ww.txt)). The CSME version is unstated. Sibling Lenovo notes cite 19.0.5.x against Intel's August 2026 fix level 19.0.11 for Arrow Lake S/HX ([INTEL-SA-01427](https://www.intel.com/content/www/us/en/security-center/advisory/intel-sa-01427.html)), so ours is probably older (inference); that is a security matter, not stall evidence. No newer firmware exists to flash, and I found no source showing macOS loads Intel microcode files itself (inference).

**Confidence:** High for revisions and BIOS state; Low for any link to I-116 or I-118.

### 2.5 The I-118 evidence cannot tell an automatic reset from a hang ended by a power cycle, and no firmware watchdog fits

In N-292 four OpenCore starts in a row ended at `EB|LOG:EXITBS:START` after two Ubuntu probe sessions, with no macOS output or panic ([N-292 README](evidence/native/N-292/README.md)). That line marks where OpenCore's log stops, not where the machine died: the passing cold boot N-293 ends on the identical line (`evidence/native/N-293/opencore-2026-10-27-174540.txt`). The handoff still asks what the screen showed. "15 to 40 s after EXITBS" is an upper bound that includes firmware POST and possibly a manual power press. From the log stamps I computed 33, 25 and 19 seconds from each EXITBS to the next OpenCore start; a shrinking interval is not what a fixed timer gives. The first start was slower in firmware (229 ms against 68 to 81 ms at "Boot order has first option as the default option"), consistent with a cold start but not proof, so "warm-only" is unproven.

The UEFI boot-services watchdog defaults to five minutes and stops at ExitBootServices ([UEFI 2.11](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html)); OpenCore also clears it, and all six logs print `OC: Watchdog status is 0` ([Configuration.tex](https://github.com/acidanthera/OpenCorePkg/blob/master/Docs/Configuration.tex)). Linux's iTCO heartbeat defaults to 30 s, inside the window ([iTCO_wdt.c](https://github.com/torvalds/linux/blob/master/drivers/watchdog/iTCO_wdt.c)), but N-274's dmesg has no iTCO line, so the driver probably never bound. Aspect 15 also said OpenCore reports reset causes through `StartupPowerEvents`; that is wrong, the option only sets a Data Hub property ([Configuration.tex](https://github.com/acidanthera/OpenCorePkg/blob/master/Docs/Configuration.tex)). The firmware reset register is an SMI write (port 0xB2, per Aspect 15), so a reset may run SMM code (inference).

**Confidence:** Medium (logs and sources read directly; whether any restart was automatic is unknown).

### 2.6 State that could survive a restart after Linux: GSP, microcode, VT-d

The mechanism with the best public precedent is the NVIDIA GSP. Its protected region (WPR2) stays up when Linux unbinds the driver ([nova-core unload v5](https://lore.gitlab.freedesktop.org/drm-ai-reviews/20260515-nova-unload-v5-0-c4d6250ad160@nvidia.com/T/), [mxtools PR 559](https://github.molgen.mpg.de/mariux64/mxtools/pull/559)), and the open module fails early with `NV_ERR_INVALID_STATE` when it finds WPR2 already up ([kernel_gsp.c](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c)); a GB203 report describes WPR2 latched across warm reboots ([open-gpu 1353](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1353)). Our probe started nouveau on the GB206 with GSP RM 570.144 ([dmesg](evidence/native/N-274/hw/dmesg.txt)). Against it: those failures appear as a failed GPU init in the next OS, not a silent reset, and a Hybrid boot keeps the dGPU idle.

Microcode comes second. An OS-applied update lasts until power is removed; kernel documentation does not say so and I could not confirm it for this CPU, though 2019 reports on older Intel parts treated it as normal ([Arch FS#64498](https://bugs.archlinux.org/task/64498), [USN-4182-3](https://ubuntu.com/security/notices/USN-4182-3)). N-274 did not update (0x11b before and after); whether the 10-24 sessions loaded 0x121 or 0x122 is unknown and takes one dmesg line to settle. Third, Linux skips disabling VT-d translation for an Intel iGPU with device ID prefix 0x7d, and it fired in N-274 ([iommu.c](https://github.com/torvalds/linux/blob/master/drivers/iommu/intel/iommu.c)); a platform reset clears DMAR registers, so carryover is unlikely (inference). The EC is a candidate with no evidence either way.

**Confidence:** Low (each carryover mechanism is plausible and none is shown).

### 2.7 Arrow Lake Hackintosh practice: VT-d off, X2APIC gating, MADT type 9, and a Legion that does not follow the pattern

The community's EXITBS cure is VT-d off: 1401 2.6.0 added a BIOS checklist item for 12th-gen and newer Intel including Core Ultra, because it got machines past `EXITBS:START` (1401 #10, #11, #53, #58) ([changelog](https://github.com/nullmoth/1401/blob/main/CHANGELOG.md)). On an Insyde laptop the VT-d row was hidden behind X2APIC and turning X2APIC off exposed it; the same thread found `ProvideCurrentCpuInfo = true` mandatory on Arrow Lake-H, found `CpuTopologyRebuild` made failures unrecoverable, and cleared an APFS respawn loop with `SetApfsTrimTimeout 0` ([1401 #58](https://github.com/nullmoth/1401/issues/58)). 1401's own Arrow Lake laptop default enables CpuTopologyRebuild, which that reporter's test contradicts; we keep it off. 275HX reports in [#44](https://github.com/nullmoth/1401/issues/44) and [#49](https://github.com/nullmoth/1401/issues/49) show the same handoff stop. DevirtualiseMmio guidance is split: off on laptops, on for Core Ultra 200 desktops ([changelog](https://github.com/nullmoth/1401/blob/main/CHANGELOG.md)).

The Legion breaks the pattern. Linux sees DMAR with two DRHDs and VT-d active for graphics ([dmesg](evidence/native/N-274/hw/dmesg.txt)), so firmware VT-d is on, yet N-293 reaches the desktop with `DisableIoMapper` set (`docs/session-handoff.md`). So "VT-d off" is not universal. This is inference: the community's "hang at EXITBS" reports may also be a last log line, as in 2.5. Our MADT fix (only type 9 entries, `APIC-LAPIC.aml`) is ours, confirmed on a second 275HX laptop per Aspect 14 (not re-checked).

**Confidence:** Medium (1401 text read 2026-10-27; second-laptop confirmation not re-verified).

### 2.8 A decisive, cheap I-116 experiment: separate the waker, the instrumentation and the C-state

Treat the waker as a hypothesis. XeGfx 0.0.44 added `xegfx.irqoff_check=0` and 0.0.45 added `xegfx.gtawake=1|2`, so the levers exist. Once the cheaper steps below have run, run a 2 by 2 through xe-guard (waker on/off, `gtawake` 0/2), with a fixed load (disk copy loop plus WindowServer), recording time to stall and a stopping rule fixed in advance (for example stop an arm pair after three stalls in one arm and none in the other, or after a session budget). A 30 minute arm may show nothing, since N-290 passed 900 s and died at 88 minutes, and every stall ends in a panic or a hang with the risk of APFS rollback, so the budget should be small. The last uncontrolled death came at 88 minutes under APFS resize I/O ([N-290 README](evidence/native/N-290/README.md)), so one session per arm is meaningless.

Add readers: try `powermetrics` for C-state residency, and if it is empty add the core/package MSRs and 0x34 to LegionCpuProbe (a kext change). Before it, run one session with `debug.legioncpu.{pl,hwp,epp}` at stock values (a sysctl, no kext change and no reboot), because LegionCpuPower 0.4.1 was loaded in N-290 and Linux ran at stock limits. Then add a control arm with low-priority spinner threads that keep cores out of C6; it also changes power, temperature and the LegionCpuPower guard (10 W steps at 100 C), so it is not a clean C-state control: if stalls vanish, the cause is idle-state related and ARL037 gains weight; if not, drop it. After the next panic, read the MCA banks from 0x401 on first boot (survival across a warm reset is unverified). Raising `slto_us` (a boot-arg, so an NVRAM write that needs Bash's OK) shows whether a stall is finite, but only for stalls between the old and the new timeout, and it may waste a reboot; a TSC-gap log in XeGfx answers the same question passively. Never pair it with `tlbto_us=0`, which turns the panic into a trace line and loses the one artifact I-116 produces. A weak comparison is Linux: the 47-minute N-274 capture had no stall, but it ran without WindowServer, XeGfx or LegionCpuPower and at stock power limits, so it differs in at least four ways; a 2-hour Ubuntu run with the same disk loop and an iGPU workload shows whether the platform alone stalls.

**Confidence:** Medium (design is sound; none of these runs exists yet).

### 2.9 A decisive, cheap I-118 protocol: four columns and four arms

Add to every attempt row: cold or warm, microcode before and after, GPU mode (Discrete or Hybrid), and a phone photo of the verbose screen. Then run arms three times each. A: Ubuntu probe, log `dmesg | grep -i microcode`, `iTCO`, `wdt`, `WPR2`, then full power-off and a 30-second wait before macOS. B: same session, then a plain warm restart. C: as B, but with `nouveau` blacklisted so Linux never starts GSP. D: macOS-only warm restarts as baseline. Add a POST-time calibration (time a deliberate power press) to learn what "15 to 40 s" can contain.

Reading it: if A passes and B fails, power-retained state matters, and C separates GPU from microcode (a pass in C points at GSP/WPR2; a grep of the NvGfx log for "unexpected WPR2 already up" backs it). If B fails with equal microcode before and after, microcode is out. A long gap before the next POST means a manual power cycle is part of the story. All of it uses the existing probe stick.

**Confidence:** Medium (cheap and falsifiable; no arm has been run).

### Theme 2 key insights

1. **Each leading I-116 explanation covers only part of the evidence.** ARL037 gives one silent core but not 23 silent CPUs ([Intel 834774](https://cdrdv2-public.intel.com/834774/834774_024.pdf), [xnu mp.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c)), and the similar Xe reports keep their kernels alive ([xe 9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/issues/9168)). So I-116 is more likely a machine-wide stall than one core's idle exit. Confidence: Low.
2. **"C-state" is untested, not disproved.** `max_cstate=2` still allows a C6-class state ([intel_idle.c](https://github.com/torvalds/linux/blob/master/drivers/idle/intel_idle.c), [Unraid](https://forums.unraid.net/topic/197400-intel_idle-not-registering-native-c-states-on-intel-core-ultra-200-series-arrow-lake-model-0xc6/)), XCPM thinks the CPU is Comet Lake, nothing publishes residency, and the waker result is confounded. Confidence: Medium.
3. **"EXITBS" in I-118 labels where OpenCore's log stops, not where the machine died.** Passing and failing boots end identically and no firmware watchdog is known to cover 15 to 40 seconds (iTCO, TCO, ME and EC watchdogs are not excluded; Unverified) (`evidence/native/N-293/opencore-2026-10-27-174540.txt`, [UEFI 2.11](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html)). Find the real stage and whether a human ended it before testing hypotheses. Confidence: Medium.
4. **Cold versus warm is the variable both problems share and neither has recorded.** Intel's triager asks for it ([i915 16052](https://gitlab.freedesktop.org/drm/i915/kernel/-/issues/16052)), NVIDIA's WPR2 reports hinge on it ([open-gpu 1353](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1353)), and N-293 passed cold where N-292 failed after Linux. One column fixes this at no cost. Confidence: Medium.
5. **No firmware fix is known to exist, so there is none to wait for.** The BIOS is newest, newer microcode has no public ARL037 mapping, and ARL037 is Planned Fix ([Lenovo](https://download.lenovo.com/consumer/mobiles/s2cn26ww.txt), [microcode 20260811](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/releases/tag/microcode-20260811)). I-116 work is a driver-side workaround or a measurement. That the BIOS is the newest is checked; that no fix exists is an absence claim from one search pass. Confidence: Medium.

### 3.2 ArrowWhatever's userptr unwire race window also exists in our xg_vm.c, but it is not the I-116 signature

[ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever) patches NvGfx and XeGfx on the same silicon as ours (275HX, 7d67, macOS 26.7.1). Its [userptr note](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/userptr-panic.md) describes a panic with the text `xegfx: vm: freeing wired page ... (ref 0x1)`. Pin and unwire lock separately, so the last unwire decides a page is free, and while it prepares the free outside the lock another thread pins the same page; the page reaches the free list still wired. The [patch](https://github.com/Mountainatic/ArrowWhatever/blob/main/patches/0001-xg_vm-userptr-race.patch) adds one unwire entry that drops the count and unlinks the run under `xg_vm_mtx`, plus a guard in `vm_page_free()` for user-held pages. The author reports a soak with zero panics; the README says the project is mainly LLM-driven, and nobody else has reproduced it.

I read our [xe-2.6.2 xg_vm.c](https://github.com/watchthelight-labs/NvGfx/blob/xe-2.6.2/gpu/xegfx/shim/src/fbsd/xg_vm.c) against that. The lookup takes the mutex and returns ([lines 442-455](https://github.com/watchthelight-labs/NvGfx/blob/xe-2.6.2/gpu/xegfx/shim/src/fbsd/xg_vm.c#L442-L455)); the pin path then raises `ref_count` with an unlocked add ([1744-1810](https://github.com/watchthelight-labs/NvGfx/blob/xe-2.6.2/gpu/xegfx/shim/src/fbsd/xg_vm.c#L1744-L1810)); unwire drops and frees outside the lock ([894-910](https://github.com/watchthelight-labs/NvGfx/blob/xe-2.6.2/gpu/xegfx/shim/src/fbsd/xg_vm.c#L894-L910)). The window is real in our tree.

It is a latent race, not our current failure. None of the captures I checked, N-290 included, carries the `freeing wired page` text; I-116 is a whole-machine stall that ends in a CPU rendezvous panic with 23 of 24 CPUs stuck (local, `evidence/native/N-290`). This is inference: the race may need more WindowServer or Metal-client churn than our runs reached. The patch files are under the same [PolyForm Noncommercial](https://github.com/Mountainatic/ArrowWhatever) licence as our fork.

**Confidence:** Medium (checked 2026-10-27) that the window exists (our code read); Low that it explains anything we saw; Unverified for the soak (self-reported).

### 3.3 zep245's NVRAM trace cost and GT hold are cheap A/B tests, and its "TLB flush timeout" name is a trap

[zep245's design log](https://github.com/zep245/IrisXe-macos-driver/blob/main/DESIGN.md) (a Tiger Lake machine) has two findings that map onto I-116. First, NVRAM breadcrumbs: a flip took about 700 ms because the commit-trace patch wrote and synced NVRAM about 37 times per atomic commit, against about 1.3 ms with the flip off; dropping the breadcrumbs after WindowServer opened the framebuffer fixed it (b125, b126). Ours writes `xegfx-step` and `xegfx-accel` and calls an NVRAM sync in [`xg_trace_write`](https://github.com/watchthelight-labs/NvGfx/blob/xe-2.6.2/gpu/xegfx/shim/src/xnu/xg_kext.cpp), switched by `xegfx.nvram_trace`, and every guard capture from N-223 to N-290 ran with it at 1 (local, `evidence/native/N-2xx/guard/sysctl.txt`). The trace-off run has never been done; how often we call it, and what our NVRAM backend costs, are unmeasured.

Second, the GT hold: dropping the boot-time keep-awake hold led to a panic 16 s after a cold boot, so zep245 holds through boot and releases 90 s after attach (b148); a one-shot RC6 test later showed that allowing RC6 was fine (b139). XeGfx 0.0.45 carries `gtawake=1|2` and `irqoff_check=0` as A/B switches (local, handoff). The panic line needs care: "NMIPI for unresponsive processor: TLB flush timeout" is an [xnu CPU-side message](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c) about a CPU that did not answer a TLB shootdown with interrupts off. It is not a GPU or GuC invalidation timeout such as the one tracked in [xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678).

Do not over-read the fit. A GT hold is not expected to cure the GuC late-ack bug (the A/B in 8678), and XeGfx [skips the media GT](https://github.com/watchthelight-labs/NvGfx/tree/xe-2.6.2/gpu/xegfx), so the Wa_22016122933 root cause cannot explain I-116. These tests probe a possible separate CPU-side cause.

**Confidence:** Medium (checked 2026-10-27) that the NVRAM cost is real on zep245's machine (own log); Unverified that it applies to ours.

### 3.4 Intel Xe peers compared with XeGfx: nobody has a proven daily driver on Arrow Lake, including us

Our state: [XeGfx](https://github.com/watchthelight-labs/XeGfx) 0.0.45 first reached stages 1 to 4 on 2026-10-21 ([issue 2](https://github.com/watchthelight-labs/XeGfx/issues/2)), and the accelerated desktop ran 88 minutes at N-290 before I-116 killed it (local, handoff). It is not a daily driver, and the stall is unresolved.

[ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever) is the only peer on our silicon. It claims a zero-copy GGTT flip and a deferred K9 flip at about 60 fps ([zero-copy](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/zero-copy-flip.md), [K9](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/k9-deferred-flip.md)), with manual bring-up after boot and one WindowServer restart ([route](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/route.md)). The aspect report rated it tier S; the audit rates it B (self-reported, LLM-driven, no reproduction), and the audit wins. [jwx29's meteor-lake-local](https://github.com/jwx29/NvGfx/tree/meteor-lake-local) (155H, 7d55, macOS 15.8.1) passes stages 1 to 7 and says stability was not established; our review found a small glue delta on our 0.0.44 and no I-116 fix (local open loop). [VedCloud](https://github.com/VedCloud/Meteor-Lake-Xe-LPG-Metal-Graphics) (MTL-U 7d45) reports a lost-wakeup GuC TLB timeout fixed.

Two projects are not competitors. [WhateverXe](https://github.com/b00t0x/WhateverXe) 0.6.1 says no Xe-LPG or Meteor Lake support is planned. [nmx-intel](https://github.com/kitsuneislife/nmx-intel) (Raptor Lake) composites on NVIDIA and flips to the Intel panel, a Hybrid fallback idea rather than an Xe driver. NullMoth's own NMXGPU has an open report where i915/xe never attach on Arrow Lake-H ([297](https://github.com/nullmoth/nvidia-macos-driver/issues/297)). Breadth for every Xe peer is "anecdote" ([scout](https://github.com/watchthelight-labs/research/blob/main/scout/xe/2026-10-27.md)).

**Confidence:** Medium (checked 2026-10-27) for the ranking; every peer claim is self-reported (tier B at best).

### 3.5 MPS translation failures on NVIDIA are open upstream, and one patch is not safe to copy

Geekbench 6 and 7 hit `depthwiseConv_3x3` with "Function vs Private pointer phi" in [377](https://github.com/nullmoth/nvidia-macos-driver/issues/377), the same kernel's CPU translation exceeds 180 s in [111](https://github.com/nullmoth/nvidia-macos-driver/issues/111), and Vision barcode detection aborts its host app in [334](https://github.com/nullmoth/nvidia-macos-driver/issues/334). The maintainer's position in 334 is that the kernel does not run on the GPU yet and that a private-pointer fix faults the GPU. So a translation that "succeeds" with null handles is a different failure from a clean error. PR [385](https://github.com/nullmoth/nvidia-macos-driver/pull/385) is the one candidate, and we carry it.

Issue [419](https://github.com/nullmoth/nvidia-macos-driver/issues/419) (Chrome WebGL2 context loss on 2.6.2) reports a local patch that cut translation failures from 53 to 0 and null handles from 24 to 0, with 18,066 frames at 64.5 fps, by retrying forward-fields four rounds. It conflicts with 385. The translator crate is [LGPL-3.0-or-later](https://github.com/nullmoth/nvidia-macos-driver/blob/main/translator/translator/Cargo.toml), so reuse is allowed, while the repository's top level states no standard licence ([LICENSE](https://github.com/nullmoth/nvidia-macos-driver/blob/main/LICENSE)). This is inference: because a GPU-fault outcome exists, "failures dropped to zero" is not proof of correct rendering.

**Confidence:** High (checked 2026-10-27) that the failures are open and seen by several reporters; Low on 419's effect (one anecdote).

### 3.6 Window-drag stalls: one independent measurement supports our commits, and two state-cache commits carry a regression

Issue [412](https://github.com/nullmoth/nvidia-macos-driver/issues/412) is a tester on an RTX 5080 reporting stock 2.6.2 dragging at 85 to 100 flips per second with 63 to 124 ms stalls, and six of our commits removing them. Two state-cache commits made Alacritty text jump back, so the tester held them out. By commit message those match our [repeat-pipeline skip](https://github.com/watchthelight-labs/NvGfx/commit/f0864ceca324) and [sampler-variant memo](https://github.com/watchthelight-labs/NvGfx/commit/a8c3288e3f92) (inference: the match is by message and switch name); in our package both sit behind `NVMTL_NO_PSO_SKIP` and `NVMTL_NO_SV_MEMO`. The commit-time pass on its own queue is [fc07ff5e145d](https://github.com/watchthelight-labs/NvGfx/commit/fc07ff5e145d).

Related reports point at the same area without proof: a missed frame about every 0.6 s on all apps ([410](https://github.com/nullmoth/nvidia-macos-driver/issues/410)) and frame pacing at 540 Hz ([302](https://github.com/nullmoth/nvidia-macos-driver/issues/302)). For N-294 the practical test is a heavily redrawing terminal (such as Claude Code itself) with the two switches on and off.

**Confidence:** Medium (checked 2026-10-27); one independent tester, and the regression is one report.

### 3.7 HiDPI scaled modes: the hi-res flag and a pixel-rate rule explain more than the earlier "1.3x ceiling"

Scaled modes validate but never reach the list in [354](https://github.com/nullmoth/nvidia-macos-driver/issues/354), which points at `kDisplayModeValidForHiResFlag` (0x00800000) missing in `getInformationForDisplayMode` (nvrm-fb.cpp line 3028 at 2.6.2). Issue [360](https://github.com/nullmoth/nvidia-macos-driver/issues/360) reports 1920x1200 HiDPI refused at 165 Hz but accepted at 60 Hz, and [341](https://github.com/nullmoth/nvidia-macos-driver/issues/341) covers HiDPI above half native on 1440p and 1600p panels.

Three corrections to the aspect report. The limit fits a desktop pixel rate (width x height x refresh) better than a ratio cap, with display stream compression and link bandwidth as caveats; "about 1.3x" was a simplification. The 12-byte versus 16-byte scale-resolutions tension between macOS 15 and 26 was largely settled by a later 15.8.1 data point (16-byte also hidden, 12-byte with backing sizes works). And the 12-byte finding in 341 came from our own account, so it is not independent. The community hacks (a 64-timing cap with `nvfbscalehz`, a 26-byte NVRM patch) are unvalidated by anyone else.

**Confidence:** Medium (checked 2026-10-27); the flag is code reading plus our mode list, the rate rule is a fit to three reports (inference).

### 3.8 HDR stays blocked by one self-reported trace; Chrome flicker is cured by turning Graphite off

HDR is an old request ([30](https://github.com/nullmoth/nvidia-macos-driver/issues/30)). The only mechanism offered is that CoreDisplay forces 8 bits per component when the framebuffer class name contains "NVDA", and that renaming it kills the Metal compositor; that trace in [341](https://github.com/nullmoth/nvidia-macos-driver/issues/341) came from our own account, so the aspect report's framing as a community finding is wrong. Treat it as one unreproduced trace.

Chrome flicker has a measured cure: Skia Graphite disabled fixed it in [333](https://github.com/nullmoth/nvidia-macos-driver/issues/333), and `NVMTL_SCHEDULE_AFTER_SURFACE_WRITES=1` cured the Simulator flicker at a speed cost in [293](https://github.com/nullmoth/nvidia-macos-driver/issues/293). On our box Chrome 155 runs Graphite on the NVMTL plugin; a launcher without it exists, effect unconfirmed (local note, 2026-10-22). ANGLE Metal on NVIDIA was opened for Discord in [348](https://github.com/nullmoth/nvidia-macos-driver/issues/348) (closed).

**Confidence:** Low (checked 2026-10-27) for HDR (single self-reported trace); Medium for the Graphite cure (few reporters).

### 3.9 Blackwell laptop power: one GSP control lifts 50 W to 115 W for us, and the upstream platform handler gap is open

On our machine the RM gets no platform power input by default, the VBIOS limit is 50 W, and Windows runs the same GPU at 115 W ([power.md](https://github.com/watchthelight-labs/NvGfx/blob/nvgfx-2.6.2/notes/power.md)). GSP control 0x20800AD2 (`CONFIGURE_TGP_MODE`, in [ctrl2080internal.h](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080internal.h)) lifts the enforced limit, and boot-arg `nvrmtgp=1` sends it from [nvrm_power.cpp](https://github.com/watchthelight-labs/NvGfx/blob/nvgfx-2.6.2/kexts/NVRM/nvrm_power.cpp) on AC. NVIDIA's [laptop comparison](https://www.nvidia.com/en-us/geforce/laptops/compare/) gives a 50 to 100 W TGP range for the 5070. I could not extract the figure from Lenovo's [PSREF sheet](https://psref.lenovo.com/syspool/Sys/PDF/Legion/Legion_5_15IAX10/Legion_5_15IAX10_Spec.PDF) here, so reconciling the three numbers is open.

Upstream shows the same problem class on Linux: [1389](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1389) (Lenovo RTX 5070 Mobile, `_DSM NVD1` not found), [1393](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1393) (platform request handler fails, power capped), [1344](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1344) (closed; Legion capped near 55 W) and [1162](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1162) (NVPCF not bound). The aspect report suggested diffing 615.71.10 for the 1389 fix. Checked: [615.71.10](https://github.com/NVIDIA/open-gpu-kernel-modules/compare/615.71.09...615.71.10) is 615.71.09 plus a version bump, and the [615.71.09 to 615.78.08 diff](https://github.com/NVIDIA/open-gpu-kernel-modules/compare/615.71.09...615.78.08) shows no platform-request or power-policy logic change, only regenerated GSP firmware data and unrelated files. This is inference: any fix lives in the firmware blobs, which a source diff cannot show.

GSP stability issues in the same tracker (heartbeat Xid 119 in [1353](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1353), frozen power telemetry in [1237](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1237) and [1287](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1287), a boot hang in [1421](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1421)) are why the TGP step stays conservative: AC only, polled, on change.

**Confidence:** High (checked 2026-10-27) for the 50 W to 115 W control on our machine (our N-73 measurement); Low for any upstream fix location; Unverified for Lenovo's own figure.

### 3.10 The firmware-memory panic is real, and the panic string alone does not name the cause

[LegionCbmrFix](https://github.com/watchthelight-labs/LegionCbmrFix) (our public repo) unloads Microsoft's `cbmr_driver.efi`, which this BIOS loads at 0x180000000, and reserves its 164 KiB. Without it the Legion panicked in `vm_page_validate_no_references` within 4.5 to 10 minutes of memory churn, with or without GPU drivers; the README records a 360 s churn test passing and no panic of this kind since 2026-10-16. [jwx29's README](https://github.com/jwx29/NvGfx/tree/meteor-lake-local) reports the same panic on its Meteor Lake machine and confirms the workaround unloads the image there, but says post-workaround stability was not established.

The same panic text appears in NullMoth issue [328](https://github.com/nullmoth/nvidia-macos-driver/issues/328) on a different laptop (GTX 1650), at a page address far outside our CBMR range. This is inference: that report is not the firmware-memory case, and the panic string alone cannot decide. Matching on the text will misattribute.

**Confidence:** High (checked 2026-10-27) for the Legion cause and fix (own machine, README test); Low for any other machine.

### Theme 3 key insights
1. The Intel work is converging on the same two suspects, and neither is the GPU. ArrowWhatever's userptr race (a lock gap in pin and unwire) and zep245's NVRAM cost (syncs in a hot path) are both glue-code bugs, both plausible in XeGfx, and neither matches I-116's signature. They are cheap to close. The userptr race is unlikely to be the cure; the NVRAM trace is a different matter, because native NVRAM writes on EDK2-derived firmware normally run in System Management Mode (whether this Insyde build does is Unverified), so the trace is a cause candidate and not only hygiene. Sources: [userptr note](https://github.com/Mountainatic/ArrowWhatever/blob/main/docs/userptr-panic.md), [DESIGN.md](https://github.com/zep245/IrisXe-macos-driver/blob/main/DESIGN.md). Confidence: Medium.
2. Third-party evidence on both vendors is thin, and part of it is ours. The HDR trace and the 12-byte HiDPI finding came from our own account, the drag measurement is one tester, and the ArrowWhatever soak is self-reported. What is independent: the MPS failures (several reporters) and the Chrome Graphite cure. Sources: [341](https://github.com/nullmoth/nvidia-macos-driver/issues/341), [412](https://github.com/nullmoth/nvidia-macos-driver/issues/412), [377](https://github.com/nullmoth/nvidia-macos-driver/issues/377). Confidence: Medium.
3. A readable N-294 result needs the base change split from our changes. 2.6.2 carries the 2.5.5 driver, and our package adds fixes for MPS, sampler slots, scaled modes and drag, so the result should be logged against both sets, with the two state-cache switches and a cold-cache note. Sources: [release](https://github.com/nullmoth/nvidia-macos-driver/releases/tag/v2.6.2), [412](https://github.com/nullmoth/nvidia-macos-driver/issues/412), [370](https://github.com/nullmoth/nvidia-macos-driver/issues/370). Confidence: Medium.
4. Panic text identifies less than it seems to. `vm_page_validate_no_references` also appears off-range on another laptop, and "TLB flush timeout" is a CPU shootdown in xnu while the Xe tracker uses the phrase for GPU-side invalidation. Read the address and the stack, not the headline. Sources: [LegionCbmrFix](https://github.com/watchthelight-labs/LegionCbmrFix), [328](https://github.com/nullmoth/nvidia-macos-driver/issues/328), [xnu mp.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c). Confidence: High.
5. The Blackwell power question changed from "find upstream's fix" to "ours is the fix". The 615.71.10 and 615.78.08 diffs show no platform logic change, and our one GSP control already lifts 50 W to 115 W, so waiting on upstream source buys little; the open items (envelope numbers, blob changes) are documentation work. Sources: [compare](https://github.com/NVIDIA/open-gpu-kernel-modules/compare/615.71.09...615.78.08), [power.md](https://github.com/watchthelight-labs/NvGfx/blob/nvgfx-2.6.2/notes/power.md), [1389](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1389). Confidence: Medium.

## Theme 4: macOS Tahoe 26.7.2, MT7925 Wi-Fi and Bluetooth, and Legion Gen 10 Hackintosh reports

### 4.1 macOS 26.7.2 final is build 25G332 (2026-10-26); the "25G330" in our earlier notes is release candidate 3

AppleDB lists four 26.7.2 builds: [25G320](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G320.json) (RC, 2026-10-06), [25G325](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G325.json) (RC2, 2026-10-13), [25G330](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G330.json) (RC3, 2026-10-19) and [25G332](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G332.json) (release, 2026-10-26). Dortania's KDK is tagged [25G330](https://github.com/dortania/KdkSupportPkg/releases/tag/25G330), and our own maintainer reply in [mt7925-hackintosh-wifi issue 4](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/4) first said "25G330" before correcting itself to 25G332. Where an aspect report or tracker row calls 26.7.2 "25G330", the later verified record wins: the final build is 25G332.

I checked on the Legion today that Apple's catalog still serves several builds: `softwareupdate --list-full-installers` lists 26.7.2 as 25G332 and as 25G325, and does not list 25G330. The rebuilt 25G332 kernel reports `xnu-12377.161.15.701.48~2` (Darwin 25.6.0, built 2026-10-12), against `700.19~2` on the Legion's 25G241. The Darwin version is the same on both, so a gate keyed on it cannot tell them apart; only the xnu tag can. The Intel delta patches for 25G330 and 25G332 give identical BootKernelExtensions.kc, SystemKernelExtensions.kc and kernel (25G325 differs). This is inference: a 25G330 tester's kernel-side behaviour is therefore a fair proxy for 25G332, but only for those three files.

**Confidence:** High (checked 2026-10-27): dates from AppleDB, catalog listing and kernel string read by me.

### 4.2 The 26.7.2 kernel collections can be rebuilt offline from the 25G241 files and Apple's Intel delta OTA, and the result is verified byte for byte

Apple serves an Intel delta from 25G241 to 25G332, [1,358,475,023 bytes and readable with HTTP Range, listed in the appledb entry](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G332.json), so only the needed members are fetched. It holds BXDIFF50 patches for BootKernelExtensions.kc (about 1.7 MB), SystemKernelExtensions.kc (about 0.6 MB) and the kernel (about 1.5 MB), in the format [blacktop/ipsw implements](https://github.com/blacktop/ipsw/blob/master/pkg/ota/bxdiff50/bxdiff50.go): a header with sizes, a 20-byte result SHA-1 and a 20-byte base SHA-1, then compressed control, diff and extra streams.

What I verified myself: each patch's base SHA-1 equals the SHA-1 of the live 25G241 file on the Legion; the patched output's SHA-1 equals the patch's result SHA-1; and its size and CRC32 equal the entries in the OTA's own `post.bom`. That is a byte-level fact, not a plausibility argument. Kext binaries have lived only inside these two collections since Ventura and Apple ships them prebuilt (only the auxiliary collection is built on the Mac), so the rebuilt files hold every kext binary the 25G332 boot uses, including IO80211Family 1200.13.1, the version in the issue 4 reporter's logs.

Nothing was installed and no Apple binary goes into git. The route needs the exact base build, so it works from 25G241 only, and it covers kernel-side files only: for user-space files the OTA gives just a bill of materials (see 4.5). The scripts were standard-library Python, run with `-I` on files in a scratch directory.

**Confidence:** High (checked 2026-10-27): hash, size and CRC32 equalities were computed, not reported.

### 4.3 kcabi finds the 25G332 layouts unchanged and three real function differences; whether they matter to MtkWlanNative is unsettled

[kcabi](https://github.com/watchthelight-labs/kcabi) compares IO80211Family, IOSkywalkFamily and AppleBCMWLAN between two kernel collections: instance sizes, vtables, request tables and disassembled functions. Against 25G241, the sizes, vtables and request tables are unchanged. Of 1154 compared functions, 1121 are identical and 33 differ; 31 of those differ only in addresses or ordering. The three real differences are one field offset in `_kern_netif_queue_rx_enqueue` (0x4d8 becomes 0x4e8) and the immediates in `AppleBCMWLANNANInterface::enableDatapath` and `::disableDatapath`. By my arithmetic every changed immediate in the two NAN functions moves by exactly 0x27, which looks like one inserted structure rather than six unrelated edits.

This is inference: the NAN (Wi-Fi Aware) functions are in Apple's Broadcom driver class, which MtkWlanNative does not subclass, so they probably do not matter to us. The `rx_enqueue` change is the one to read, because a field moving by 0x10 inside a queue structure breaks any code that accesses that field directly instead of calling an API. Whether MtkWlanNative does is not settled; it needs a disassembly review of the call site and a boot test on a real 25G332 machine. kcabi compares binaries, not behaviour, so unchanged layouts do not prove the Wi-Fi menu will attach.

**Confidence:** High for the measured differences, Unverified for their consequences (checked 2026-10-27): no 25G332 boot of our kexts has happened.

### 4.4 MtkWlanNative declines 25G332 on the xnu tag alone, so the public break is a gate decision rather than a measured incompatibility

[MtkNativeAbi.hpp](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi-native/blob/main/src/MtkNativeAbi.hpp) starts the native front end only when the running kernel's xnu tag is on an allow-list and the live class sizes match. The shipped allow-list in [the same repository](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi-native) has one entry, 25G241 (`700.19~2`). A refusal is recorded in the provider property `MtkNativeDeclined`; `MtkNativeLast` exists only when the front end started. After a decline MtkWlan falls back to its Ethernet front end: `en1` with no Wi-Fi port.

That matches [issue 4](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/4): MtkWlan 0.12.1 and MtkWlanNative 0.4.13 load, `en1` is up, no Wi-Fi menu, and the maintainer reply gives the same diagnosis. The reporter's empty `MtkNativeLast` is consistent with a decline but is not proof, and nobody has captured `MtkNativeDeclined` yet, so the real refusal reason is unrecorded. This is inference: with the tag outside the list the size check never runs, so the unchanged sizes of 4.3 could not have helped. The reporter is on a desktop board with a MediaTek card, not a Legion, but the gate does not depend on the motherboard.

**Confidence:** Medium (checked 2026-10-27): code reading is direct, the link to the reporter's machine is inference.

### 4.5 LegionBtFix is pinned to 25G241's bluetoothd, which changed in place in 26.7.2; the page hashes were not checked against it

[LegionBtFix](https://github.com/watchthelight-labs/LegionBtFix) patches two instructions of `bluetoothd` in memory and gates on a byte window plus a SHA-1 of the whole 4 KB page, for 25G241 only. The OTA bill of materials lists `/usr/sbin/bluetoothd` at the same size in both builds (23,555,568 bytes) with different CRC32 values, so the binary changed without growing, and Apple's [26.7.2 notes](https://support.apple.com/en-us/149522) include one Bluetooth entry. Bluetooth patterns are known to be build-specific: [BrcmPatchRAM issue 39](https://github.com/acidanthera/BrcmPatchRAM/issues/39) is a bluetoothd pattern that stopped matching. This is inference: the page-hash gate will probably refuse on 25G332, the safe outcome, but the I-047 crash loop could then return unprotected.

I could not apply the bluetoothd delta to check the pages. The patch's base SHA-1 equals neither the live universal binary nor its x86_64 slice. For five other files I compared (bluetoothaudiod, bluetoothuserd, `true`, cfprefsd, airportd) the live CRC32 equals the OTA's `pre.bom`, but bluetoothd does not (live 2381493249, `pre.bom` 4287939534). I have no explanation: an earlier modification of the on-disk binary and a BOM that records the file in another representation are both possible. It does not change the conclusion that LegionBtFix is untested on 25G332.

**Confidence:** Medium for "binary changed" (BOM comparison), Unverified for the page hashes (checked 2026-10-27).

### 4.6 The one 25G332 reporter's Bluetooth returned after a power drain, which points at card state rather than the OS version

In issue 4 the reporter's first USB listing showed [no MediaTek device](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/4); the maintainer advised a full power drain and a BIOS Bluetooth check; later that day he wrote that Bluetooth works and posted a listing with a "Wireless_Device" at vendor 5075, product 13826, which is 13D3:3602 in hex (my conversion; the line order in his paste is ambiguous). The step he took is not recorded, and his Wi-Fi is still unresolved, which fits 4.4.

The ID is in [Linux btusb v7.3](https://github.com/torvalds/linux/blob/v7.3/drivers/bluetooth/btusb.c), and [MtkBt](https://github.com/watchthelight-labs/mt7925-hackintosh-bluetooth) matches by vendor (Foxconn 0489, IMC Networks 13D3, MediaTek 0E8D), so it would claim the device. This is inference: a Bluetooth function that is missing from the USB bus and returns after a power cycle looks like a combo-card state fault, and our own [issue 1](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/1) already documents the card wedging over a warm restart. Whether LegionBtFix or MtkBt loaded on his desktop was not asked. A tracker row saying "Bluetooth lost on 26.7.2" would overstate this evidence, and so would "26.7.2 is Bluetooth-safe".

**Confidence:** Medium (checked 2026-10-27): one anecdote with an unrecorded fix.

### 4.7 Apple's 26.7.2 security notes are large and touch the kernel, Bluetooth, Wi-Fi and graphics components, but say nothing about kext layouts

I parsed the CSAF data behind [APPLE-SA-149522](https://support.apple.com/en-us/149522): 213 CVE entries under 93 component headings, among them Kernel (17 entries), Bluetooth (1), Wi-Fi (3), AirPort (1) and graphics components (IOSurface, Metal, IOGPUFamily). The notes describe fixes, not ABI, so they cannot tell us whether IO80211 or IOSkywalk layouts moved; 4.3 does that. They do show that a rule of "only the kernel tag changed" would be false.

For NvGfx and XeGfx the only point is that graphics-family components changed. No report in the corpus tests an NVIDIA or Intel iGPU driver on 25G332, and no Arrow Lake data on 26.7.2 turned up. The day-one reports are from stacks that avoid private IO80211 layouts: [InsanelyMac's 26.7.2 thread](https://www.insanelymac.com/forum/topic/363378-release-macos-tahoe-2672) has users on itlwm, SimpleBCM and SimpleHDA updating to 25G332 without trouble, and I found no acidanthera issue or commit that mentions 26.7.2.

**Confidence:** High on the counts (parsed), Low on what they imply for our drivers (checked 2026-10-27).

### 4.8 Intel Macs end at Tahoe, which makes staying on 26.x workable but each point release a recurring ABI cost

Apple's [macOS page](https://www.apple.com/os/macos/) lists macOS 27 "Golden Gate" as compatible with Apple silicon Macs only, which agrees with the [OCLP discussion](https://github.com/dortania/OpenCore-Legacy-Patcher/issues/1183) that Tahoe is the last Intel release. How long Intel Macs keep receiving Tahoe security updates is only [press-relayed](https://sixcolors.com/post/2025/06/macos-tahoe-is-the-last-release-to-support-intel/) (three years), not a primary Apple statement.

For the Legion this matches Bash's position of staying on Tahoe 26.x until support ends. The cost is that every point release moves the xnu tag, can change bluetoothd (4.5) and user-space daemons (the OTA bill of materials shows `airportd` growing from 3,228,064 to 3,228,096 bytes), and so re-opens the per-build pins of MtkWlanNative and LegionBtFix. This is inference: automating the kcabi refresh and the OTA route (4.2) is worth more than any single 25G332 fix.

**Confidence:** Medium (checked 2026-10-27): the model list is direct, the support horizon is press-relayed.

### 4.9 Other MT7925 projects for macOS are new, share the per-build pin and have no 25G332 results; Linux has fixes that mirror our open problems

The set, with creation dates from the GitHub API: [laobamac/SimpleMtkWlan](https://github.com/laobamac/SimpleMtkWlan) (2026-05-26, GPL-2.0), [flxxxxddd/SimpleMtkWlan v1.5.0](https://github.com/flxxxxddd/SimpleMtkWlan/releases/tag/v1.5.0) (2026-10-13), [mnnobre/AirportMtkWlan](https://github.com/mnnobre/AirportMtkWlan/issues/2) (2026-10-14), [thanhnndev/mt7925-macos-wifi](https://github.com/thanhnndev/mt7925-macos-wifi) and [HackSucks/mtwlm](https://github.com/HackSucks/mtwlm) (both 2026-10-26), and an unread fork of our own repo. The thanhnndev README calls itself experimental, mostly AI-written and tested on one laptop; it reports native mode on 25G241 at 176.6 Mb/s down and 65.0 Mb/s up (HE 160 MHz, 2x2), WPA2-PSK and mixed WPA/WPA2 only, and keeps `abi/native-wifi/` dumps for 24H32 and 25G241. It is tied to one build exactly as ours is, so the 26.7.2 wall is shared by everyone on the private IO80211 front end.

On the Linux side, [ac22c8c723c6](https://github.com/torvalds/linux/commit/ac22c8c723c6) keeps the join ROC until the station is authorized (the 4-way handshake area), [d12a54be2604](https://github.com/torvalds/linux/commit/d12a54be2604), [8d2f5990cd42](https://github.com/torvalds/linux/commit/8d2f5990cd42) and [c781b74c3fd0](https://github.com/torvalds/linux/commit/c781b74c3fd0) harden power-management and reset paths (our I-081 warm-restart problem), and [b3078bb2ee12](https://github.com/torvalds/linux/commit/b3078bb2ee12) and [e3ac0d9f1a20](https://github.com/torvalds/linux/commit/e3ac0d9f1a20) reset on a WMT timeout and accept short FUNC_CTRL events (MtkBt's "status 255"). The [linux-firmware repository](https://gitlab.com/kernel-firmware/linux-firmware) has MT7925 builds stamped 20261016; our kexts embed 20260813, and no changelog exists for either. This is inference: these fixes address symptoms like ours, but a subject line is not a diff, and each needs a read against MtkWlan before anyone claims it applies.

**Confidence:** Medium (checked 2026-10-27): repository and commit facts are direct, performance claims are anecdotes, applicability is untested.

### 4.10 Arrow Lake Hackintosh reports converge on VT-d off or a DMAR drop and a type-0 MADT; two other 275HX EFIs differ from ours in exactly the two Booter quirks of our I-118 question

The most-reported fix for the silent stop at `EXITBS:START` on Arrow Lake is VT-d off: [1401 issue 10](https://github.com/nullmoth/1401/issues/10), [issue 11](https://github.com/nullmoth/1401/issues/11), the [2.6.0 changelog](https://github.com/nullmoth/1401/blob/main/CHANGELOG.md) and the `core-ultra-drop-dmar` rule in [efi_rules.json](https://github.com/nullmoth/1401/blob/main/p1401/efi_rules.json). [Issue 58](https://github.com/nullmoth/1401/issues/58), the best-documented chain, found the VT-d row greyed out until X2APIC was disabled (an Insyde laptop), then needed `ProvideCurrentCpuInfo` and `SetApfsTrimTimeout` 0; the reporter changed VT-d and the DMAR drop in one boot, so causality is two variables. The same rule file scopes `arrow-lake-ctr` to desktops, and a laptop default panicked in that issue.

Reading the actual plists, [wsjj's Y9000P EFI](https://github.com/wsjj-official/EFI-2025Y9000P) (83F5, 275HX, BE200 Wi-Fi, panel on the NVIDIA GPU) and the [ASUS FX608LP EFI](https://github.com/CENSEDAXIS20025/ASUS-FX608LP-Hackintosh-Multiboot) both set `SetupVirtualMap` true and `ForceExitBootServices` false. Our OCEFI (read today) is the reverse, with `DevirtualiseMmio` off, `ProvideCurrentCpuInfo` on, and only the APIC table in ACPI Delete (no DMAR drop). [Mountainatic's YaoShi16 EFI](https://github.com/Mountainatic/YaoShi16-Ultra-OpenCore-efi) reports the same MADT shape (tier B, not re-checked) on a second 275HX laptop with a converted `APIC-LAPIC.aml` and deletes both DMAR and APIC. wsjj's README says `ResizeAppleGpuBars = -1` while its plist has 0, so documentation drifts from config.

This is inference: the Booter difference is a candidate A/B for our resets after `EXITBS:START` (I-118), not a proven cause, and "VT-d off yields a type-0 MADT" is unverified because nobody has dumped the MADT before and after a BIOS change. None of these EFIs reports I-118-style resets.

**Confidence:** Medium (checked 2026-10-27): plist values and issue text are direct, causality is absent.

### 4.11 Lenovo-specific evidence is thin: LenovoLegionLinux carries our model's EC data, and the nearest hackintosh Legion repo is Raptor Lake

[LenovoLegionLinux commit a897adf92a06](https://github.com/johnfanv2/LenovoLegionLinux/commit/a897adf92a06) (2026-08-07) adds the Legion 5 15IAX10 (83F0) with BIOS prefix `S2CN` and EC chip ID 0x5508, shared with the LOQ 15IRX10, and [29571790b209](https://github.com/johnfanv2/LenovoLegionLinux/commit/29571790b209) (2026-09-20) uses a level-index, speed-only WMI fan table across the 0x5508 models, citing level bytes at EC addresses F9F0 to F9F9. Our BIOS is S2CN26WW, so this is data about our own EC. This is inference: it is a read-only cross-check for the LegionFan curve code in LegionCpuPower, not something to write to.

[BelikPePe-UA/legion5-15irx10-hackintosh](https://github.com/BelikPePe-UA/legion5-15irx10-hackintosh) is a Legion 5 15IRX10 with an i7-14700HX (Raptor Lake) on Sequoia, with Fn+Q mode events from WMI notify 0xE3 and GPU clock tools. It helps with keyboard and GPU power, not with Arrow Lake boot questions. In [1401 issue 44](https://github.com/nullmoth/1401/issues/44) a Lenovo 275HX owner reports an early page fault with no answer. No 285HX, Legion 16IAX10 or Legion Pro Gen 10 report turned up.

**Confidence:** Medium on the EC commits (direct), Low on usefulness (checked 2026-10-27).

### Theme 4 key insights
1. **The Wi-Fi break on 26.7.2 is a safety decision in our own gate: the layouts kcabi checks are unchanged, but three function differences are unreviewed.** Bluetooth is a separate question, since bluetoothd changed in place. The gate refuses on the xnu tag before it looks at sizes (4.4), while the offline kcabi run shows unchanged sizes, vtables and request tables with only one plausibly relevant function change (4.3). The cheapest next step is to review that one change and, with Bash's agreement, try an allow-list entry for reporters, not to wait for a full re-port. The unknown is real: no 25G332 boot of our kexts has happened. Confidence: Medium. Sources: [MtkNativeAbi.hpp](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi-native/blob/main/src/MtkNativeAbi.hpp), [kcabi](https://github.com/watchthelight-labs/kcabi).
2. **Offline reconstruction separates ABI preparation from the decision to update.** Because the 25G332 kernel collections can be rebuilt and verified without installing anything (4.2), dumps, allow-list candidates and header refreshes can be prepared while the Legion stays on 25G241, and the same OTA's bill of materials already shows which user-space files changed (bluetoothd, airportd, 4.5 and 4.8), which kcabi cannot see. Confidence: High on the method, Medium on its reach. Sources: [bxdiff50.go](https://github.com/blacktop/ipsw/blob/master/pkg/ota/bxdiff50/bxdiff50.go), [APPLE-SA-149522](https://support.apple.com/en-us/149522).
3. **Bluetooth reports on 26.7.2 mix two causes, so neither "the update broke it" nor "the update is safe" follows.** The bluetoothd binary changed at an unchanged size and Apple lists a Bluetooth fix, so LegionBtFix's pins are likely stale (4.5). Separately, the one reporter's Bluetooth device left the USB bus and returned after a power drain, which is a card-state fault our warm-restart issue already describes (4.6). Confidence: Medium. Sources: [LegionBtFix](https://github.com/watchthelight-labs/LegionBtFix), [issue 4](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/4), [issue 1](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/1).
4. **Outside Arrow Lake configs support a read-only BIOS look and an optional two-quirk A/B for I-118.** Two other 275HX EFIs (not independent of each other's guide lineage, and neither reports a Linux-then-macOS sequence, which is where I-118 appears) run SetupVirtualMap on without ForceExitBootServices and the 1401 corpus converges on VT-d off or a DMAR drop, whereas ours has the opposite quirk pair and keeps DMAR (4.10). None of them reports I-118-style resets, so the A/B is a hypothesis, and our normal boots work. Confidence: Medium. Sources: [ASUS FX608LP EFI](https://github.com/CENSEDAXIS20025/ASUS-FX608LP-Hackintosh-Multiboot), [wsjj EFI](https://github.com/wsjj-official/EFI-2025Y9000P), [1401 issue 10](https://github.com/nullmoth/1401/issues/10).
5. **Staying on Tahoe 26.x is viable, but each point release is a recurring cost for private-layout kexts, and the newest competitor shares it.** macOS 27 drops Intel while 26.7.2 still carries a large security update (4.7, 4.8), and each release moves the xnu tag, bluetoothd and possibly user-space daemons; the newest MT7925 project has the same per-build pin (4.9). Automating the kcabi refresh and the OTA route is worth more than any single 25G332 fix. Confidence: Medium. Sources: [Apple macOS page](https://www.apple.com/os/macos/), [thanhnndev/mt7925-macos-wifi](https://github.com/thanhnndev/mt7925-macos-wifi).

## Technical and operational details

This section collects the reference material that the findings above lean on: how to read the I-116 panic, the firmware and device identity of the 7D67 iGPU, the verified offline route to the 26.7.2 kernel collections, and the experiment matrices for I-116 and I-118. ### Reading the I-116 panic string

The panic text says that the panicking CPU timed out in `mp_rv_action` with 23 of 24 CPUs having entered. In the public xnu source the rendezvous spin is bounded by four times the lock timeout (`mp_spin_timeout`), the lock timeout defaults to 0.5 s on release kernels, and the boot-arg `slto_us` changes it ([xnu mp.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c), [machine_routines.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/machine_routines.c)). The TLB-shootdown timeout follows the same default and a boot-arg `tlbto_us=0` turns the panic into a trace event. Two consequences follow. First, "23 of 24" means exactly one CPU never arrived at the rendezvous, but the panic string does not print which one, so the most useful extra datum a future panic could carry is the identity and last instruction of the missing CPU. Second, the later "none of the other 23 CPUs acked the NMI" phase is a separate observation: one stuck CPU explains the first phase, while the second needs something shared, such as an SMM/SMI period, a fabric or memory stall, or CPUs that cannot take an NMI. The independent contradiction check in this research run left the question unresolved, and no public report shows the same two-phase pattern on a 7D67 part. The public xnu tree ends at xnu-12377.121.6 while the Legion runs a 12377.161.x kernel, so mapping panic offsets to source is approximate.

Gleixner's remark on LKML (2026-01-13) is the best published statement of what a stuck MMIO transaction looks like to an operating system: the machine "just stalls on outstanding MMIO transactions w/o further notice" and the NMI is "a red herring" ([LKML](https://lkml.iu.edu/2601.1/13033.html)). It argues for looking at the first stalled access rather than at the NMI silence. It does not by itself explain why 23 CPUs spinning in cache would also ignore an NMI.

### Verified offline route to the 26.7.2 kernel collections (no install)

The 26.7.2 release candidates were 25G320, 25G325 and 25G330 (RC3); the shipping build is 25G332, released 2026-10-26 ([appledb 25G332](https://github.com/littlebyteorg/appledb/blob/main/osFiles/macOS/25x%20-%2026.x/25G332.json)). The kernel collections cannot be downloaded as plain files, but the Intel delta OTA from 25G241 carries them as BXDIFF50 patches against the files already on this Mac. The route, as run and checked by the research agents:

1. Confirm the base: `sw_vers` shows 26.7.1 / 25G241 and the SHA-1 of BootKernelExtensions.kc, SystemKernelExtensions.kc and the kernel begin 01a0b5ca, d8847772 and b42c5e15.
2. Read the OTA entry for 25G332 in appledb whose prerequisite build is 25G241 and whose device group is the seven-device Intel group (the zip is about 1.36 GB).
3. List the zip's central directory with HTTP range requests and fetch only the three `.bxdiff` members (about 12 MB).
4. Apply each patch to the live file with a small stdlib Python patcher that refuses to run unless the base SHA-1 matches and checks the result SHA-1.
5. Cross-check the rebuilt hashes against `post.bom` from the same zip, then validate with `kmutil inspect`.
6. Dump and compare with the project's own kcabi tooling against `abi/native-wifi/25G241`.

The rebuilt 25G330 and 25G332 collections have identical hashes for BKC, SKC and kernel, so for kext purposes they are one build. The kcabi comparison against 25G241 shows unchanged class sizes, vtables and request tables, with three small differences: one field in `_kern_netif_queue_rx_enqueue` moves from offset 0x4d8 to 0x4e8, and two immediates change in `AppleBCMWLANNANInterface::enableDatapath` and `disableDatapath`. Whether those break MtkWlanNative is inference until someone reviews them. Nothing in this route touches OCEFI, NVRAM, kexts or the volume. The build identities come from [appledb](https://github.com/littlebyteorg/appledb). An independent check confirmed that the patch headers carry base SHA-1s matching this Mac's files, but that check did not apply a patch itself; the byte-level result rests on the first agent's run, whose patcher verified each result SHA-1 against the OTA's own manifest.

Record, for every probe-then-macOS pair, whether the machine was fully powered off in between; this turns the cold-versus-warm column from memory into data. ## Tradeoffs and alternatives

The research did not produce one clean answer for any of the open issues, so the useful comparison is between the options the evidence leaves open. Each pair below states what the public record says about the two sides and where the project's own constraints change the weighting.

**An i915 port against an xe port for the Intel iGPU.** XeGfx carries Linux i915 plus Mesa ANV. On this PCI ID i915 is the upstream default driver and has been since the force_probe requirement for Meteor Lake was removed in v6.7 ([commit 213c43676beb](https://github.com/torvalds/linux/commit/213c43676beb5f5a63cb27a0c8e8e71035b08445)), while xe still carries `require_force_probe` for the Meteor Lake and Arrow Lake descriptors, so running xe on this silicon is an officially unsupported configuration. The tracker reality points the other way: every active Intel investigation of the Arrow Lake GuC acknowledgement stall lives in the xe tracker ([xe 8678](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678), [xe 9168](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168)), while an Intel developer answered a wedge report on xe with "Use i915?" ([xe 9224](https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9224)). There is also a data point that the two drivers diverge on the same PCI ID: 7D67 shows corruption under i915 at DDR5 7600 MT/s and above that xe does not show ([i915 17098](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/17098)), which is far above a laptop's SO-DIMM speeds but proves the memory paths differ. For a port, i915 is the larger shim surface and xe the smaller one (GuC is mandatory there and the `force_execlist` parameter was dropped on 2026-06-30, [commit b623bd790db0](https://github.com/torvalds/linux/commit/b623bd790db0)). Staying on i915 keeps the code the maintainers still treat as the shipping path; moving to xe would make the project track the code where Intel's engineers are currently debugging. Neither is clearly better for I-116, and a switch would restart the bring-up work.

**GuC submission against execlists.** GuC submission with HuC through the GSC is the default for Meteor Lake and Arrow Lake in i915, and upstream does not offer execlists as a supported fallback in xe. A user on Raptor Lake reported that a GuC hard lockup went away with `enable_guc=0` ([i915 15708](https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/15708)), but that is a different platform with different firmware, and GuC deprivilege on Meteor Lake means the firmware sets up the WOPCM before the OS starts. The cheaper variant of the same idea is to send TLB invalidation through the MMIO fallback instead of a GuC H2G message. It would test the GuC CT path without abandoning GuC submission, but it is not a one-flag change: Meteor Lake is the one platform that needs GuC invalidation, and GuC-based GGTT invalidation is documented as incompatible with MMIO invalidation ([commit af58ee227662](https://github.com/torvalds/linux/commit/af58ee227662)). The experiment matrix lists it with that warning.

**Holding the GT awake against letting it idle.** A forcewake or RC6-off hold is the one mitigation that two independent non-Arrow-Lake ports report as helping: the FreeBSD drm-kmod maintainer's Meteor Lake case ([drm-kmod 457](https://github.com/freebsd/drm-kmod/issues/457)) and the zep245 macOS port notes. The costs are power and heat on a laptop that already runs at 100 C on a CPU lap, and the counter-evidence is direct: the owner of the xe 8678 investigation pinned the GT at C0 with zero C6 residency and still saw nine acknowledgement timeouts. The two readings are compatible if the xe bug is GuC-side (a late reply) while the macOS stall is CPU-side (a write that blocks), which is why the experiment is worth running as a 2x2 with the waker thread instead of being assumed to work.

**Hybrid composite route against XeGfx driving WindowServer.** In Hybrid mode the iGPU owns the panel. The conservative route lets NvGfx composite on the NVIDIA GPU and lets a small framebuffer driver flip scanout on the iGPU, which the nmx-intel project demonstrated on Raptor Lake ([nmx-intel](https://github.com/kitsuneislife/nmx-intel)). It does not depend on the XeGfx stall being solved. XeGfx drives WindowServer directly, which is the only route that can give a Metal-accelerated desktop on the iGPU alone, and it is also the route with the I-116 stalls. The two are fallbacks for each other as long as the Discrete NVIDIA boot remains the daily driver.

**Stay on 26.7.1 against moving to 26.7.2.** The offline route recovers the 26.7.2 collections without installing, so the decision no longer depends on first updating a machine to look. The remaining tradeoff is between per-build ABI pins and a fingerprint approach. Per-build pins are safe but fail at day one of every update, as the first public 25G332 report on the project's own native Wi-Fi shows ([mt7925-hackintosh-wifi issue 4](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi/issues/4)). A fingerprint over class sizes and vtable slots accepts a new build only when the layout is unchanged. The horizon is bounded in any case: macOS 27 is Apple silicon only, so Tahoe is the last Intel release ([OCLP issue 1183](https://github.com/dortania/OpenCore-Legacy-Patcher/issues/1183)).

**A native Wi-Fi front end against a layout-independent driver.** MtkWlanNative integrates with the private IO80211 and Skywalk classes, which gives the system Wi-Fi menu but ties each release to a build. The Intel-card projects that avoid private layouts, such as the itlwm line and SimpleBCM ([itlwm](https://github.com/laobamac/itlwm/releases), [SimpleBCM](https://github.com/laobamac/SimpleBCM)), were reported working on 26.7.2 on day one. For MT7925 itself, no layout-independent driver exists, and the two public native MT7925 lines (ours and [thanhnndev's](https://github.com/thanhnndev/mt7925-macos-wifi)) report WPA2 joins only, with no 6 GHz, AWDL or sleep support. Swapping the card for an Intel one is what most Gen 10 Hackintosh EFIs do ([wsjj EFI](https://github.com/wsjj-official/EFI-2025Y9000P)), at the cost of opening the laptop and of the Bluetooth path.

**VT-d off or DMAR dropped against VT-d left on with an APIC replacement.** The Arrow Lake community splits. Several desktops and laptops pass the ExitBootServices stop only with VT-d off or the DMAR table dropped, and the 1401 maintainers encode that as a rule ([efi_rules.json](https://github.com/nullmoth/1401/blob/main/p1401/efi_rules.json)). Other 275HX laptops boot with VT-d on, DMAR deleted and a custom APIC table ([YaoShi16 EFI](https://github.com/Mountainatic/YaoShi16-Ultra-OpenCore-efi)). The Legion keeps DMAR and replaces the APIC table, and its normal boots pass. VT-d state is the one variable that has never been recorded for the failing I-118 boots, so changing it now would add a variable, while recording it would not.

**Newer microcode through OpenCore against waiting for a Lenovo BIOS.** Microcode 0x11b is two Intel releases behind (0x121 and 0x122 exist), and Lenovo's newest BIOS for this machine, S2CN26WW, only updated CSME. Loading newer microcode over an older BIOS revision has broken boot on other Intel parts in 2026 ([microcode issue 112](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/issues/112)), and no public text ties either newer revision to the one open erratum (ARL037). The expected value of loading it as a stability fix is low and the downside is a non-booting machine, so it is a last-resort experiment and not a mitigation.

### 2. By question

#### Q1 Freezes on MTL/ARL (R1 to R14, R22)
Agree: a stage of recoverable TLB-ack timeouts (26 in 47 h, 20 to 60 per day) often precedes silent freezes; the freezes leave nothing in the journal and the NMI watchdog stays quiet (R5, R6); xe is worse than i915 on the same machine (R6, R12); kernel upgrades helped most (Aspect 4). Non-Linux ports (R8, R9) independently found that keeping the GT out of RC6 or parked cures their hang. Disagree: causes. Intel-side fix for acks is cache coherency (R2); FreeBSD and zep245 blame RC6 transitions plus delayed interrupt handling; R4 and R5 blame display DSB/DC; Intel calls R3 a power-sequencing race. Confounded mitigations: `psr/dc/ASPM/C-state` results are mixed and often changed together (R7), several "fixes" were kernel or BIOS updates in disguise, and R2's all-domain forcewake hold did not stop the ack delay while R8/R9 holds did cure a harder stall, so the two symptoms may differ. The single IRQ-pinning report (R7) is unconfirmed. New: Intel's own ARL-H CI silently dies in many unrelated selftests (R11), which fits a platform-level stop rather than one GuC path; caveat: "incomplete" can also mean lost logs. No report matches I-116 (23 of 24 CPUs answer) on 7D67 in any OS.

#### Q2 NVIDIA via NullMoth (R15 to R23)
Agree: 2.6.2 is stable enough that users measure rather than crash-report; MPS, Vision, Geekbench compute remain broken on every generation; drag stalls come from per-upload IOSurface import and VRAM re-import (R17); HiDPI needs the hi-res flag and hits a head-scaler ceiling (R18); HDR is blocked by the "NVDA" class path (R19); Chrome flicker goes away with Graphite off (R20); Blackwell laptop users get almost no NVIDIA help and TGP only lifts through platform negotiation (R23). Disagree: scaler ceiling 1.3x vs 1.4x; 12-byte vs 16-byte scale-resolutions by macOS version; the maintainer says the hang is gone in 2.5.2 while 377 shows translation still fails. Confounded: R22's idle freezes survived 60 Hz and flip_latch=2 (so those are not cures); reinstall fixed one "regression" (NullMoth 259, NEW); fixes in downstream forks are single-machine and often AI-assisted, which upstream refuses.

#### Q3 Intel Xe on macOS (R9, R24 to R26)
Agree: all four Xe-on-xnu stacks (Mountainatic, jwx29, VedCloud, zep245) keep the firmware-lit panel, activate by hand after boot, descend from NullMoth's tree, and say stability is not established; none reports a multi-hour soak; their panics are the same classes (thread_call cap, preemption_level, userptr free, TLB flush timeout, firmware pages). WhateverXe and JulioNectar stay on Gen12. No third-party issue or reply exists on any of these repos (NEW check). NullMoth's own Intel driver is on hold (297).

#### Q4 macOS 26.7.2 (R27 to R30)
Agree: day-one reports from stacks that do not touch private IO80211 layouts (itlwm, SimpleBCM, Lilu kexts) are clean; the only public break is ours (native Wi-Fi gate). No acidanthera issue or commit mentions 26.7.2 or 25G332 (NEW scan). Disagree: whether the BT loss in R27 is the update or hardware state. Confounded: R27's Bluetooth returned after a suggested power drain, but the step actually taken is unknown, and the reporter's board differs from R28's working 25G241 report; 25G330 is an RC, 25G332 is final (kgp and our own notes used the wrong one first).

#### Q5 MT7925 and Legion Gen 10 (R27 to R30)
Agree: two native lines run MT7925 on Tahoe (ours, thanhnndev), WPA2 only at about 90 to 180 Mb/s, no 6 GHz, AWDL or sleep; warm restart can wedge the card until a cold power-off (our mt7925 1; Linux mt76 reset fixes). Gen 10 Hackintoshes elsewhere mostly swap in Intel Wi-Fi (wsjj Y9000P BE200, ASUS FX608LP). Disagree: WPA3 (BelikPePe says works, thanhnndev no confirmed WPA3). NEW: AppleALC PR 975 (Ersiter, 10-27) adds ALC287 layout 99 for Legion IAX10H, https://github.com/acidanthera/AppleALC/pull/975.

#### Q6 Resets after ExitBootServices (R31 to R33)
Agree: nobody has posted an Arrow Lake case of a reset (as opposed to a hang) after EXITBS; hang advice is VT-d off (X2APIC first on some Insyde laptops), MADT type 9, DevirtualiseMmio. Practitioners treat a cold power cycle as the cure when a prior OS left hardware in a state (R32, R33). Disagree: VT-d (our post to 1401 says DMAR is still exposed on our boot, others require it off); CpuTopologyRebuild and SetupVirtualMap on or off. Confounded: hang advice does not transfer to a warm-only reset. Negative search today (1401, NullMoth, acidanthera for reset/reboot/after Ubuntu/Windows) found nothing.

### 2. Counterclaims

**C1 (High). The best-known root cause cannot be ours.** Wa_22016122933 is scoped to the media GT; XeGfx skips that GT in seven boots (V6). The xe fix is untested on 7D67 and says nothing about GT0 (the xe owner told a GT0 wedge reporter that her series "would not have prevented this", note 26). Do not write "I-116 is the 2.3 s cache bug". https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678

**C2 (High). Linux freezes are mostly a different class from N-290.** 9168 (ARL-H 7dd1): the freeze came in the same second as the timeout, but the kernel stayed alive (journal kept writing, SysRq-S ran), `nmi_watchdog=panic` never fired. 9168 note 4 (today, ARL-H 7dd1): timeouts come minutes to hours before the freeze, kernel alive, 4 power-offs in one day. N-290 is the opposite: all other CPUs silent to NMI for 0.5 s, then a panic. https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168

**C3 (High). A forcewake hold does not cure the TLB-ack bug** (V18). Answer to the brief: no, a hold would not stop the xe 8678 stall; it is GuC-side (8 to 9 doorbell kicks ignored, worst 5996 ms) until the cache theory. But XeGfx's problem may be CPU-side (a doorbell write that blocks), which the hold could still help. Two separate mechanisms; the corpus merges them.

**C4 (Medium-High). Setup-specific.** Same silicon, same XeGfx 0.0.44, same macOS build did a 40-minute soak with zero stalls (local evidence). N-290 died at 88 min under an APFS resize (heavy I/O, NVIDIA boot). Suspect the I/O, the dGPU, the BIOS or config before the TLB path.

**C5 (Medium). ARL037 is a weak fit.** Intel text: C6 or deeper entry/exit, no MCE, synthetic only, BIOS workaround possible. It hangs a core within a module, not 23 of 24 CPUs. 9168 note 4 froze four times with `intel_idle.max_cstate=2`, `xe.enable_dc=0`, PSR and FBC off. Newer microcode is not documented to fix it. Keep it as a low-probability lead, not a cause. https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/9168

**C6 (Medium). "Wa applied, platform still dies."** xe 8678 note 28: the owner's 7d51 machine locked completely on 2026-09-16 on a kernel with the WA, with no log line at all and the NMI/pstore route capturing nothing. So even on Linux a silent whole-platform death exists that the cache fix does not explain. It is the closest published analogue of N-290, but 7d51 is not 7D67. https://gitlab.freedesktop.org/drm/xe/kernel/-/work_items/8678

**C7 (Medium). Every free sends an H2G is overstated** (V3). The free-worker and execbuf stacks may still be one event, but through a different gate than "every free".

**C8 (Medium). 2.3 s late ack vs a stall that outlasts the panic path.** A late ack is a fence timeout while all CPUs run. N-290 reads in two phases (panic-string-133823.txt, xnu mp.c): CPU 5 timed out in `mp_rv_action` after 2.0 s with 23 of 24 CPUs entered, so one CPU never arrived (id not printed). Then in `mp_kdp_enter` none of the other 23 CPUs acked even an NMI (1 ack of 24, two 0.5 s waits). A single stuck CPU explains phase one; phase two needs a shared stall (SMM/SMI, fabric or memory, iGPU DMA with VT-d off) or CPUs unable to take NMIs. An uncached MMIO write to a hung target stalls only the issuing core (reasoning, Unverified).

**C9 (Low). Possible shim analogue of the cache bug on GT0.** If the shim maps GuC shared memory cacheable while the GGTT side is snooped differently, a stale-line effect could appear on GT0 too. Untested idea, no source. Check how `xg_vm.c` maps CTB pages and what PAT the GGTT entries use.

**C10 (Low). Leads that do not match.** i915 17098 (7D67 corruption with DDR5 at 7600 MT/s or above, i915 not xe): https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/17098 (not re-fetched). Oct 2026 execbuf presumed_offset fault fixes: not relevant to a stall.

### 4. Unresolved debates

1. **Late ack or blocked doorbell?** I-116's frame is a CPU-side write inside `intel_guc_ct_send`. The Linux bug is a CPU-side read of a stale reply. Different mechanisms; nothing published shows the write side stalling.
2. **One stuck CPU or the whole machine?** The rendezvous count (23 of 24 entered) favours one CPU that never arrived; the NMI silence of the other 23 favours a machine-wide stall. The panic string does not name the missing CPU: the "NMI pending" list is every CPU except the panicking CPU 5. Candidates (CPU-side MMIO wait, SMM/SMI, fabric/memory, iGPU DMA) are not ranked by data. A second panic with `cpu_signal` state or a kdp-free capture would be needed.
3. **Does I-116 share a cause with the Linux "silent platform death"?** C6 suggests it might; unprovable without a trace on a 7D67 part.
4. **I-118:** microcode persistence across warm reset (V15), iTCO watchdog, VT-d/DMAR state, and 16052's "cold vs warm" are all candidates. I did not re-verify the iTCO and DMAR findings of Aspect 15; they stay Unverified.

## Failure modes, risks and misconceptions

These are the ways the evidence in this dossier is most likely to mislead, grouped by theme. Each theme also lists its own limits above; this section collects the traps that matter when a result is written into project notes or a public page.

### Theme 1: I-116, the Intel iGPU stall and panic

Do not write that I-116 is the 2.3 s cache bug. Wa_22016122933 is scoped to the media GT, our log shows GT1 skipped, and the workaround's own reporter saw a silent death with it applied. The trap is borrowing a published fix's confidence for a different mechanism.

The panic's 2.0 s is a timeout, not a measurement of the stall. Reading "a 2 second hang" from it, or the 27 s figure from the N-287 README, misleads: the saved progress file contradicts the README, and the real duration is unknown.

"Forcewake hold fixes it" is two claims. It correlates with fewer whole-system freezes in two ports, each a single machine without a controlled A/B, and it did not stop the late-ack stall on Arrow Lake in xe 8678. A hold that cures I-116 would not prove the xe mechanism, and one that fails would not rule out a CPU-side blocked write.

Several sources are tier B or LLM-assisted: the Intel text on i915 16052 and 12104, the Tiger Lake port's notes, ArrowWhatever's soak, and the FreeBSD BAR2 PR 496 (single author, unreviewed). The lore patch body was not read (403). Last, load correlation is easy to over-read: N-290 is one panic during one APFS resize, and the 20 ms checker may have changed the rate, so a clean 88 minutes is a hint, not a result.

### Theme 2: platform, errata and the I-118 early resets

Anchoring on ARL037 because it is the only erratum with the right shape is the main trap: Intel's wording (synthetic, no MCE, one core) is narrower than the panic, and a machine-wide stall would make it a wrong cure. The waker "result" is one observation with a changed instrumentation set, which can hide a coincidence.

Several aspect-level statements should not enter the project notes: that OpenCore decodes reset causes, that Arrow Lake does not use `intel_idle`, that three newer microcode revisions exist, and that ARL037 is fixed on HX. Where the early research reports and the later verification checks disagree, the checks win.

For I-118, "EXITBS" is a logging boundary and "15 to 40 seconds" mixes POST and human reaction, so both look more precise than they are. The four failures also come from one sequence, so GSP, microcode and VT-d each fit all four rows and none is separated from the others. A cold pass such as N-293 (Discrete NVIDIA, VT-d on) says little about Hybrid mode or a post-Linux boot.

Finally, 1401 guidance comes mostly from desktop and Insyde laptop reports. Copying "VT-d off" or "CpuTopologyRebuild on" into a config that already passes would change behaviour for no proven gain, and any such change touches the OpenCore config and needs Bash's OK.

### Theme 3: NVIDIA and Intel Xe on macOS

The race fix could be mistaken for an I-116 fix. It closes a real window, but the failure signature differs; if the stall continues after the port, the log should say the race was removed and the stall remained.

Self-reported peers are rated B for a reason. ArrowWhatever and jwx29 are LLM-driven projects with results from one machine each and no independent reproduction. Their "stages passed" counts are bring-up milestones, not stability, and a pass on their hardware says little about ours.

The HiDPI story keeps moving. The 1.3x ceiling, the 12-byte versus 16-byte split and the missing-flag explanation have each been corrected at least once, and the flag is in our package although its effect on 26.7.1 may be nil. Do not state a cause in a public note until a mode list changes after a boot.

A 115 W control that works on AC says nothing about battery, sustained thermals or Dynamic Boost. The Linux issues describe platform handling that macOS reaches only through our opt-in boot-args, so their fixes may not transfer.

Translation counts ("53 to 0 failures") can hide a faulting GPU. Count rendered frames, GPU faults and Metal errors rather than translator statuses, and do not adopt 419 until its conflict with 385 is settled in a test.

### Theme 4: macOS 26.7.2, MT7925 and Gen 10 reports

"25G330 is the 26.7.2 release" is wrong and is already in our notes and a public reply. The identical Intel kernel files for 25G330 and 25G332 make the mistake harmless for kernel-side questions, but that equality must not be stretched to user-space files such as bluetoothd or airportd.

A clean kcabi result is not a pass. It covers three kernel families of one vendor stack; the OTA bill of materials shows `airportd` at 3,228,064 bytes on 25G241 and 3,228,096 on 25G332, so the Wi-Fi daemon changed too. The Wi-Fi menu depends on user-space behaviour kcabi cannot see, so a boot test stays necessary.

The reporter's Bluetooth recovery is easy to over-read. It is one anecdote from a desktop board, the step is unrecorded, his Wi-Fi refusal reason was never captured, and a card-state fault explains it as well as an OS change. The Legion's own bluetoothd is also unexplained: its CRC32 does not match the OTA's record of 25G241, so claims that rely on "stock 25G241" for that binary should wait until this is understood.

Hackintosh EFI repositories are not proof for our machine. They have other SMBIOS identities and other panel routing (wsjj disables the iGPU and drives the panel from the NVIDIA GPU, while our Hybrid boots use the Intel iGPU), and their documentation can drift from their plists. 1401 rules are scoped by machine class, and a rule that fixes a desktop can panic a laptop.

Some figures are not primary: the three-year Intel security horizon is press relay, and the AI-written thanhnndev README reports performance for one laptop. Neither belongs in our public pages as established fact. Absence of reports is also weak evidence: no acidanthera issue mentions 26.7.2 and no NVIDIA or Xe driver has a 25G332 report, mainly because few people have updated yet.

## Gaps and limitations

The gaps are listed by how much they change a decision, not by theme.

**No public analogue with CPU backtraces exists for an NMI-ignoring stall on this silicon.** Every public Meteor Lake and Arrow Lake freeze report found (xe 7694, 9168, 9224, i915 12104, 16937 and others) comes from Linux, and the ones that identify a mechanism describe a live kernel (SysRq works, the journal keeps writing) or a total silent death with nothing captured. None carries a per-CPU state dump comparable to the I-116 panic. The research therefore ranks mechanisms by plausibility, not by a match to a published trace, and the strongest items (the doorbell write, the TLB invalidation path, the power-state errata) are candidates. Nothing found shows the CPU-side write stall that the I-116 frame suggests.

**The one confirmed root cause for Arrow Lake GuC late acknowledgements probably does not apply.** The stale-cache-line fix (xe commit d5b0bf3f37f1, Wa_22016122933) concerns the standalone media GT. XeGfx skips that GT in every recorded boot, so the fix is relevant only if the media GT is ever brought up. The public evidence for it comes from ARL-H parts (7D51, 7DD1), not 7D67.

**Intel documentation is partial.** There is no public programmer's reference for Meteor Lake or Arrow Lake graphics, so register behaviour comes from kernel source only. The Arrow Lake specification update (revision 024, October 2026) lists ARL037 as "Planned Fix" on HX, but the column mapping was read from text extraction and from an earlier revision, and Intel does not map errata to microcode revisions in public text. Whether microcode 0x121 or 0x122 changes anything for I-116 or I-118 is unknown. The contents of Lenovo's BIOS S2CN26WW (microcode revision, SAGV, ASPM and C-state options) were inferred from sibling readmes and the revision the machine reports, not read from the firmware.

**Search reach was limited.** The shared web search budget (200 calls) was exhausted during the run, so the later work used direct fetches only, and every "no report found" statement means "none found in one pass". Specific blind spots: Chinese-language Hackintosh forums (pcbeta, the 黑果小兵 blog, bilibili); gitlab.freedesktop.org issue pages (behind a bot check, so comments came through the public GraphQL endpoint and closure reasons stayed invisible); lore.kernel.org (403, so patch bodies are quoted from tracker comments); FreeBSD Phabricator and Bugzilla; Intel's older specification-update revisions (403). The Legion Pro and 285HX Gen 10 variants have no Hackintosh reports in the sources reached.

**Self-reported project claims were not reproduced.** The Intel Xe on macOS projects (ArrowWhatever, jwx29's fork, VedCloud, zep245) publish frame rates, soak lengths and "zero panics" figures without attached logs, and several are partly built on this project's own XeGfx core. They are graded B and treated as claims. None of their longest soaks exceeds about 40 minutes, which is shorter than the failure window of I-116.

**The 26.7.2 work is byte-level only.** The kernel collections were reconstructed and checked against hashes, and a class-layout comparison against 25G241 ran, but nothing was loaded on hardware and nothing was installed. Whether the three layout differences break MtkWlanNative, and whether the build-specific Bluetooth byte patches still match, are untested. The public xnu source tag (12377.121.6) is older than the kernel the Legion runs (12377.161.x), so panic offsets map to source only approximately.

**I-118 rests on analogy.** The leading explanations (microcode persisting across a warm reboot, a Linux-armed TCO watchdog, GSP/WPR2 state left by the previous OS, a VT-d state difference) come from precedents on other CPUs or other drivers, one of them from 2019. No public report describes an Arrow Lake reset, as opposed to a hang, at that point in the boot. Nothing decisive can be said until the cold-versus-warm column and the microcode revision are recorded across a probe-then-macOS pair.

**Date and naming conflicts remain in the sources.** Two ARL037 column readings disagree about the H line in revision 008 (both agree HX is Planned Fix); a repository's commit dates read as 2026-10-28, after the day of the run; the project's own tracker calls 26.7.2 "25G330", which was the third release candidate. These are listed with the other inconsistencies in the contradictions section.

## Devil's advocate

This section keeps the objections as raised. The theme text, the key insights and the ranked actions were edited in response, so some quotations below (for example the wording of the stalled-MMIO insight and the position of the NVRAM-trace run in the list) describe the drafts before the edits. I attacked the dossier's strongest claims and its ranked actions on 2026-10-27 with read-only fetches. The factual spine held: `intel_idle` has no Arrow Lake table ([intel_idle.c](https://github.com/torvalds/linux/blob/master/drivers/idle/intel_idle.c), S, High), and S2CN26WW and microcode 0x11b are as stated. The inference on top did not: which mechanism I-116 is, which control is a control, and which experiment goes first.

### Strongest objections

1. **The stalled-MMIO reading is over-read (high).** Theme 1 says our observables "fit a stalled MMIO transaction" and leans on [Gleixner's mail](https://lkml.iu.edu/2601.1/13174.html) (A). That mail is about HPET-clocksource time failing to propagate after a hung PCI config read, so "the NMI is a red herring" is a statement about that path, not a rule. The N-287 panic CPU took an IPI (`cpu_signal_handler` sits above `fwtable_write32+0xfa` in `evidence/native/N-287/panic-string.txt`), so it was a waiter that happened to run driver code. N-288 to N-290 put the panic CPU in idle, in `pmap_remove_range` and in APFS `nx_bio_doread`: one run of four is in the driver. Both timeouts are [xnu constants](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/i386/mp.c) (S), and the silent CPU is unnamed. The data say the machine stopped answering for at least 2.5 s. They do not separate a hung uncore write, an SMI, an EC or firmware event, or a failed deep-idle wake. MMIO confidence: Low.

2. **SMM is an unnamed, testable rival (high; Low confidence).** `xegfx.nvram_trace` writes `xegfx-step` every 250 ms through native NVRAM and has been on in every guard capture since N-223. On EDK2-derived firmware, runtime variable writes are normally sent into SMM ([VariableSmmRuntimeDxe.c](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Universal/Variable/RuntimeDxe/VariableSmmRuntimeDxe.c), S), and zep245 measured about 19 ms per sync ([DESIGN.md](https://github.com/zep245/IrisXe-macos-driver), B). Whether this Insyde build does so is Unverified. An SMI stops all threads while TSC keeps counting, which fits the 2.0 s first phase; the second needs a stall that outlasts 2.5 s or recurs. The discriminator is the SMI count (MSR 0x34) plus TSC gaps. Theme 3 calls the switch "cheap to close and unlikely to be the cure" while the master list puts the run ninth.

3. **The experiment order is wrong (high).** Cheaper steps sit behind a 12-session design. (a) Set `debug.legioncpu.{pl,hwp,epp}` to stock for one session: a sysctl, no kext change, no reboot. (b) Check whether the existing LegionCpuProbe 1.1 can already read MSR 0x34 before proposing a kext change. (c) One `nvram_trace=0` run. Only then the 2x2. Thirty-minute sessions may show nothing: 0.0.43 passed 900 s and died at 88 minutes, and an arm with zero events teaches nothing. Each stall ends in a panic or hang, and an unclean end already rolled APFS file sizes back at N-293 ([N-292 README](evidence/native/N-292/README.md)). Use a stopping rule, not a fixed 12.

4. **LegionCpuPower is an uncontrolled variable (high).** Version 0.4.1 was loaded in N-290 (`evidence/native/N-290/guard/kmutil.txt`). It lifts the MCHBAR limit to 120/168 W and gives every core its own HWP range, which is MMIO and MSR traffic into the same power machinery any stall or idle-exit story involves. The I-116 themes never mention it, and Linux ran at stock limits, so it is no control for it.

5. **The controls are weaker than described (high for "another shim").** [ArrowWhatever](https://github.com/Mountainatic/ArrowWhatever) was created 2026-10-25, has 0 stars and describes itself as built on XeGfx, so it is our shim plus overlay patches. Its 40-minute soak is self-reported (B), tests its own userptr fix, and falls inside our own spread. Linux N-274 ran 47 minutes without WindowServer, XeGfx or LegionCpuPower. A read-only diff of its overlay patches against our branch is worth more than either.

6. **Firmware and idle reasoning contradict themselves (medium).** Theme 1 says the fix "may live outside every driver" and asks for "a BIOS with the pcode half"; Theme 2 says "No firmware fix exists to wait for" at High. Both rest on absence claims from one search pass. macOS does not load microcode, and no newer BIOS exists to flash. Theme 2 says the waker "adds C6 transitions" while the N-290 README says it keeps cores out of deep idle; neither is measured. The spinner arm also changes power, temperature and the guard's 10 W steps, so it is not a clean idle control.

7. **Risk and wasted reboots (medium to high).** `tlbto_us=0` makes xnu trace without panicking, which removes the one artifact I-116 yields and turns a stall into a power-button hang. A larger `slto_us` answers "does it end" only for stalls between 2 and N seconds; a TSC-gap log needs no NVRAM. On 2026-10-27 the live OCEFI config reads `SetupVirtualMap` false and `ForceExitBootServices` true, while the public EFI copy shows the reverse, so the Booter A/B changes a working, picker-less boot path and may reproduce an I-118 stop for nothing. The "per-CPU heartbeat" is a second waker. The allow-list entry looks like policy, but `MtkNativeAbi.hpp` ([source](https://github.com/watchthelight-labs/mt7925-hackintosh-wifi-native/blob/main/src/MtkNativeAbi.hpp)) is a safety gate, and kcabi's `_kern_netif_queue_rx_enqueue` field move (0x4d8 to 0x4e8) is unreviewed.

### Biases in the corpus

- **Selection.** Linux trackers hold failures; clean runs are silent. The "Linux Xe reports" class is over-represented.
- **Confirmation.** Our two hypotheses (MMIO stall, C6 and the waker) framed the queries; SMM, EC and MCA material is thin because nobody searched for it.
- **Recency and volume.** About two thirds of the sources are GitHub, many under two weeks old, and some Intel comments are LLM-assisted.
- **Vendor.** [Intel's spec update](https://cdrdv2-public.intel.com/834774/834774_024.pdf) lists what Intel found; "Planned Fix" is not "absent".
- **Survivorship and transfer.** Public ports are the ones that worked, and the forcewake-hold evidence comes from two non-Arrow-Lake ports (Tiger Lake, Meteor Lake).
- **Self-report and citation loops.** Repos like ArrowWhatever grade themselves; FreeBSD and OpenBSD import Linux i915, so agreement is not independent.

### What would change our mind

- Stalls persist at stock LegionCpuPower limits: the power kext drops out. They vanish: it becomes the lead.
- `nvram_trace=0` removes the stall: SMM or firmware cost becomes the lead, and the MMIO model drops.
- SMI count jumps across a stall, or TSC gaps appear with no SMI: that separates SMM from an uncore hang.
- A symbolized panic RIP and a named silent CPU in two runs.
- An ArrowWhatever overlay patch we lack that plausibly removes a stall.

### Decisive evidence

Per run: LegionCpuPower setting, MSR 0x34 before and after, TSC gaps, cold or warm start, time to stall, panic CPU context, under a fixed load and a stopping rule set in advance.

## Methodology

**Scope and framing.** The brief was a technical research question with an implementation-planning purpose: what the public web, up to late October 2026, knows that helps the project. The inferred type is technical research plus claim verification, with the project's own tracker rows treated as claims to check and not as ground truth. It is not a high-stakes domain in the legal or medical sense, but changes to boot configuration can leave the machine unbootable, so every action lists whether it needs Bash's explicit approval.

**Plan.** Fifteen aspects were derived from the six questions in the brief, each with queries covering a primary source, a recent source, an adversarial angle, a practitioner angle and a failure angle where they applied: GuC CT stalls (1), MMIO and forcewake (2), TLB invalidation and the free worker (3), C-states, RC6, DC and PSR (4), platform errata, microcode and BIOS (5), Arrow Lake enablement, workarounds, firmware and Mesa (6), FreeBSD and OpenBSD ports (7), NVIDIA on macOS through NullMoth and forks (8), Blackwell laptop power (9), Intel Xe on macOS (10), macOS 26.7.2 (11), offline kernel collections (12), MT7925 on macOS (13), Legion Gen 10 and Arrow Lake Hackintosh reports (14) and early resets after ExitBootServices (15).

**Execution.** The skill's `Workflow` tool was not available in this session, so the same roster ran as parallel agent calls. Wave one was fifteen aspect agents, each writing a report of 30 to 44 KB with a per-claim tier, date, confidence and direct-versus-inference label. Wave two was four agents over the whole set: a source auditor (domain counts, regrade of tiers, citation loops, weak sources, recommended removals), a contradiction hunter that also re-verified load-bearing facts independently (and corrected several), a timeline agent and a practitioner-reality agent. Four theme drafters then wrote the main findings from the aspect reports and the wave-two files, a devil's advocate attacked the drafts, and the editor assembled the dossier and applied the gate.

**Tools and reach.** Reads used `gh api` for GitHub (read-only GET), the GitLab REST and GraphQL interfaces for freedesktop.org, plain HTTP with range requests for Apple's delta OTA listing, local reads of the project's own evidence and source, and web fetches. The shared web-search budget ran out part way through, after which only direct fetches were possible. The limits that follow from this are in the gaps section.

**Tiers.** S is a primary artifact (a commit, source code, a specification or a vendor document). A is maintainer or expert text with data. B is a user report, an issue thread or a self-reported project. C is press or a blog. The auditor regraded the agents' own labels, which were inflated: by the agents' labels about 75 percent of unique URLs were S or A, by the auditor's rule-based regrade about 50 percent. The sources table uses the regrade. Every claim in the evidence table carries High, Medium, Low, Unverified or Contradicted, with the date checked (2026-10-27).

**Claim hygiene.** A claim from one self-reported repository is Unverified until reproduced. A reading of a commit message is Medium unless the source code also shows it. Anything that rests on the panic text alone, with no register offset in the report, is inference and is labelled so. Where the verification pass disagreed with an aspect report, the verification wins and the text says so.

**Privacy.** The dossier names no serials, MAC addresses, keys or recovery data. Apple download paths that embed random identifiers are cited through the appledb entry that lists them. Long hashes are shortened to the form commit messages use. Nothing downloaded from Apple or third parties is stored in the repository or run; the reconstruction of the 26.7.2 collections happened in a scratch folder.
