# legion-efi: 2026-11-21 to 2026-11-26

Read from GitHub only. Nothing below is reproduced on our machine.

- **LenovoLegionLinux 0.1.9 validated a fan-table write on a Legion 5 15IAX10 with the same BIOS family as ours (S2CN26WW).** One contributor tested an 83N2 (Core Ultra 7 255HX, RTX 5070 Laptop) on Linux. In custom power mode on AC, writing fan levels through the firmware's fan method (`\_SB.GZFD`, WMAB ids 5 and 6) landed in the EC table, read back, and ramped both fans from 2300 to 3000 RPM. Restoring the saved values returned the fans to normal. Only raising the curve was tested. The table is ten levels (1800 to 4600 RPM). It is one unit, not our 83F0, and not macOS. It does weaken the idea that no safe fan write is known for this BIOS ([commit](https://github.com/johnfanv2/LenovoLegionLinux/commit/214ef4a46aa3e96b955a52fa00887249238db8a4), [notes](https://github.com/johnfanv2/LenovoLegionLinux/commit/9ddb2e06919581a7d8f224849b596de946c92ff3)). Confidence: Medium. GPL-2.0, ideas only.
- **S2CN EC window corrected.** The firmware table puts the EC RAM window `ERAX` at 0xFE500400 (length 0xFF, two more blocks at +0x100 and +0x200). The address LLL used before read back all 0xFF. The change only affects their debug dump, but it is the first printed address for this BIOS ([commit](https://github.com/johnfanv2/LenovoLegionLinux/commit/214ef4a46aa3e96b955a52fa00887249238db8a4)). Confidence: Medium, one unit.
- **GPU temperature through WMI is empty while the dGPU idles.** On the same unit the EC's GPU temperature byte reads 0 until something queries the GPU, then holds a real value for about 20 seconds. LLL now reports "no data" for 0 ([commit](https://github.com/johnfanv2/LenovoLegionLinux/commit/fcab220cb54137da861ccc59f1ba0f72b5ed2508), [issue 668](https://github.com/johnfanv2/LenovoLegionLinux/issues/668)). Matters for any temperature readout in Hybrid mode. Confidence: Medium.
- **Instant boot works on S2CN and no OC or PL write is validated.** The two firmware flags (power on when AC or USB-PD is connected) were set and cleared and survived a cold boot. The vendor's own CPU power-limit and overclock controls read 0, so LLL hides them. The firmware attributes read PL1 70 W and PL2 125 W, writes untested ([commit](https://github.com/johnfanv2/LenovoLegionLinux/commit/7ab582e0), [docs](https://github.com/johnfanv2/LenovoLegionLinux/commit/027c8c3d)). Confidence: Medium.
- **New: a Legion 5 Pro 2025 OpenCore EFI (Core Ultra 7 255HX, macOS 26.7.2) that ships files built by this project without credit.** The EFI folder contains kexts and a driver named `org.watchthelight.*` (LegionCpuPower 0.3.3, LegionITEKbdFix 1.0.0, LegionBtFix, LegionI2CArrowLake, WTLWireless, LegionCbmrFix.efi). The README names Acidanthera and NullMoth but not us ([repo](https://github.com/KSLengYu/Legion5Pro-2025-Hackintosh), MIT). GitHub detects no licence on our repos, so this is a credit question first. Confidence: High that the files are present (bundle identifiers read), Unverified that they are unmodified.
- **Same repo: S3 sleep and wake fixes on Arrow Lake-HX.** A `GPRW` to `XPRW` rename with an SSDT that blocks wake sources 0x6D, 0x6B, 0x0D and 0x89, and an SSDT that clears `PMEE` on the XHCI and TXHC devices before `_PTS(3)` and `_PTS(5)`. Manual sleep reaches S3 and wakes. Auto sleep only turns the display off. Worth a comparison with our own wake-source list ([README](https://github.com/KSLengYu/Legion5Pro-2025-Hackintosh)). Confidence: Low, their claim.
- **Same author: a small kext that sets the Legion power mode from macOS.** `LegionECMode` calls `_SB.GZFD.WMAA(0, 0x2C, mode)` to set and `(0, 0x2D, 0)` to read, modes 1 quiet, 2 balanced, 3 performance (custom is refused), exposed as a sysctl any user can write ([repo](https://github.com/KSLengYu/LegionECMode-kext), MIT). It is the same method family our kext uses. It confirms the mode call works on a 255HX Legion under macOS. Confidence: Medium, their claim.
