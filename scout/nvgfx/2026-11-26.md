## NullMoth 3.1 and the late 2.8.1

- **3.1 (2026-11-24) is a small release: 14 commits and 20 files over 3.0.** The notes list a lock screen crash loop on RTX 30 (VFX shaders now all build, 312 of 312), a shader compiler stop on large kernels, an offline installer that finds NVIDIA's firmware package, a progress line for the 550 MB download, and the Ryzen power helper ([release](https://github.com/nullmoth/nvidia-macos-driver/releases/tag/v3.1), [compare](https://github.com/nullmoth/nvidia-macos-driver/compare/v3.0...v3.1)). Nothing in it touches hybrid panels, NMIntelFB, external displays, HDMI audio, sleep, the installer's kext list or boot-args. I compared every boot-arg name in the kexts at 2.9, 3.0 and 3.1: the 80 names are the same. Confidence: High for the diff.
- **One driver change matters to us: the boot guard now gives one answer per boot.** In 3.0 (and 2.9) NVRM raised the start counter and then NVAccel and NVRMFB read it again. On a second start after a failed one they read "2" and refused to start, with no log line, while NVRM brought the card up. The result was no accelerator and no framebuffer ([#633](https://github.com/nullmoth/nvidia-macos-driver/issues/633), [commit d06c1bef](https://github.com/nullmoth/nvidia-macos-driver/commit/d06c1bef), [nvrm_off.h](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.1/kexts/NVRM/nvrm_off.h#L40-L59)). We run 2.9 with our patches, so a boot after a failed one can hit this. Our rebase should carry the 21-line latch. Confidence: High for the code, Medium that it bites us (we have not seen the log line).
- **v2.8.1 appearing after 3.1 is a back-filled release.** Its tag commit is from 2026-11-08, the release was created that day and published on 2026-11-25. The body says only that the Mac app and the Windows tool fall back to a copy on nullmothsystems.com when GitHub downloads fail, and that the driver is unchanged from 2.8. It is not marked Latest. Why it was published late is not stated ([release](https://github.com/nullmoth/nvidia-macos-driver/releases/tag/v2.8.1)). Nothing to take. Confidence: High for the dates.
- **Hybrid mode (`nmhybrid`) is still called untested.** The doc is unchanged since 2.9 and still says it "has not run on a hybrid laptop" ([HYBRID-LAPTOPS.md](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.1/docs/HYBRID-LAPTOPS.md#L8)). The panic fix from [#555](https://github.com/nullmoth/nvidia-macos-driver/issues/555) is in 3.0 source. Two testers (Alder Lake-H, Tiger Lake-H45) then reached "panel published" with a hand-built NMIntelFB, and on both no frame ever reaches the panel: head 4 gets a pipe but the display machine never sends it a transaction. The cause of the missing pipe is in the source at [nvrm-accel.cpp line 636](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.1/kexts/NVRM/accel/nvrm-accel.cpp#L636): the panel head waits for a sysctl that nothing sets. The maintainers answered on 2026-11-14 that they have no such laptop. There has been no maintainer comment on a hybrid issue since. Whether the 3.1 package still ships the 2.9 NMIntelFB (3.0 did, per the tester's hash) could not be checked without downloading it. Confidence: High for the reports, Unverified for the 3.1 package content.
- **Other hybrid laptop reports, none answered.** A GTX 1650 on a Tiger Lake laptop works as a Metal device on 3.1 but needs a hand-built kernel collection, and `nmhybrid=1` stops at the probe step and freezes the first boot unless `nmhybriddelay=10` is set ([#649](https://github.com/nullmoth/nvidia-macos-driver/issues/649)). A muxless GTX 1650 Ti reports zero connectors and asks for a headless compute device ([#636](https://github.com/nullmoth/nvidia-macos-driver/issues/636)). An RTX 3050 laptop with an AMD iGPU asks for hybrid mode ([#640](https://github.com/nullmoth/nvidia-macos-driver/issues/640)).
- **A monitor plugged in after boot, on a laptop whose HDMI is wired to the NVIDIA GPU, still does not come up.** Boot with the cable in. A Dell G15 5530 (panel on Intel, HDMI on an RTX 4050) runs 3.1 without `nmhybrid` and reports that a cable connected at boot works, extended or mirrored, with unplug and replug, and that a cable connected later needs a WindowServer restart ([README](https://github.com/rodgod-rr/Dell-G15-5530-Hackintosh/blob/main/README.md), [#288](https://github.com/nullmoth/nvidia-macos-driver/issues/288), open). Confidence: Medium, one laptop.
- **3.0 has a driver-side brightness restore that we have not taken.** It adds a launchd job and a sysctl that give the panel level back at start when OpenCore drops NVRAM writes ([install.sh](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.0/package/install.sh#L660-L720), [nvrm-fb.cpp](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.0/kexts/NVRMFB/fb/nvrm-fb.cpp)). It only acts when the NVIDIA GPU owns the panel. Matches our brightness-after-restart problem (I-137) in Discrete mode. Confidence: High for the code, Unverified that it fixes ours.
- **RTX 50 laptops: still open items only.** An RTX 5060 Laptop with an eDP 1.4b nits panel ignores the AUX backlight writes, and the ACPI backlight call returns nothing ([#648](https://github.com/nullmoth/nvidia-macos-driver/issues/648)). A perceptual brightness curve is an open PR tested on an RTX 5080 Laptop ([#641](https://github.com/nullmoth/nvidia-macos-driver/pull/641)). AV1 and VP9 hardware decode is still missing on 3.1 ([#630](https://github.com/nullmoth/nvidia-macos-driver/issues/630)). On the ROG G16 (RTX 4060 Laptop) the WebKit GPU process cannot load the NVIDIA Metal driver because of the sandbox ([#668](https://github.com/nullmoth/nvidia-macos-driver/issues/668)); that is the blocker HighDelay's plugin works around, below.
- **HDMI monitor volume on Tahoe does nothing.** `nmhdavol=1` belongs to NMHDA, which hooks Apple's HD Audio driver; macOS 26 has none, and the audio comes from NMXAudio, which does not read the arg ([#501](https://github.com/nullmoth/nvidia-macos-driver/issues/501), [install.sh](https://github.com/nullmoth/nvidia-macos-driver/blob/v3.1/package/install.sh#L296-L307)). Confidence: Medium, inferred from the source and one report.

## Video decode in Safari (VP9, AV1)

- **HighDelay's NVK fork reports hardware VP9 decode in Safari on an RTX 2060 SUPER, Tahoe 26.7.1.** The route is a Lilu plugin (NVWebKitFixup 0.2.1 and 0.2.2) that lets WebKit's GPU process load the NVIDIA Metal runtime and register VideoToolbox decoders, plus an addon that adds VP8, VP9 and AV1 decode. AV1 is only exposed on GA10x Ampere and Ada. Turing gets VP9 but not AV1 ([commit 065fc650](https://github.com/HighDelay/nvidia-macos-driver-nvk/commit/065fc650), [video notes](https://github.com/HighDelay/nvidia-macos-driver-nvk/blob/main/video/INSTALL.md), [Safari helper doc](https://github.com/HighDelay/nvidia-macos-driver-nvk/blob/main/docs/SAFARI-WEBGL.md)). The addon is the MIT project [mickys/nvenc](https://github.com/mickys/nvenc). The release says Safari AV1 and laptop panels still need hardware tests ([v3.0.3-nvk](https://github.com/HighDelay/nvidia-macos-driver-nvk/releases/tag/v3.0.3-nvk)). Why it matters: VP9 and AV1 in Safari is one of our open problems, and this is the first concrete route. Our card is Blackwell, which none of their tests cover. Confidence: Medium that it works on Turing, Low for RTX 50. The fork has no licence asserted and descends from a PolyForm Noncommercial project, so read it for ideas only. The MIT addon is the part we could look at on its own terms.
- **A hybrid Dell with an RTX 4050 still lists VP9 and AV1 hardware decode as not working** under NullMoth 3.1 ([README](https://github.com/rodgod-rr/Dell-G15-5530-Hackintosh/blob/main/README.md)). That agrees with our own state. Confidence: High for their report.

## Idle power of the dGPU on a hybrid laptop

- **A Dell G15 5530 (iGPU on the panel, HDMI wired to the RTX 4050) runs NullMoth 3.1 and gets the RTX fully powered off at idle, 1.2 to 1.7 W package with the screen on.** Two routes. With stock NullMoth, a helper suspends the GPU through NullMoth's sleep code and cuts power with an ACPI `_OFF` method. With NVIDIA's own GC6 the author needs a patched NVRM build and these boot-args: `nvrmdynpm=2 nvrmnvpcf=1 nvregdwords=DynamicPowerManagement=3;DynamicPowerManagementVideoMemoryThreshold=0;PCIEPowerControl_<id>=39`. Wake takes about 1.2 s ([README](https://github.com/rodgod-rr/Dell-G15-5530-Hackintosh/blob/main/README.md), [CHANGELOG](https://github.com/rodgod-rr/Dell-G15-5530-Hackintosh/blob/main/CHANGELOG.md), [NVRM branch history](https://github.com/rodgod-rr/nvidia-macos-driver/commits/g15-gc6-31)). He also says NullMoth's own RTD3 cannot cut power on his laptop ([nullmoth #428](https://github.com/nullmoth/nvidia-macos-driver/issues/428)). Why it matters: it is the same shape as our dGPU idle power and GC6 questions, with a working power-cut path through an SSDT method. Confidence: Medium, one laptop, their numbers. His fork has no licence asserted (NOASSERTION), ideas only.
- **`BOOST=0` in `nvrm610.conf` keeps the RTX at P8 when on, about 12 W less** (same README). Already noted last week. Confidence: Medium.
- **HighDelay's fork adds runtime D3cold for a headless GPU.** `nvrtd3=1 nvrtd3res=<ACPI path>` with a 60 s idle period, and "Live laptop testing is required" ([backports](https://github.com/HighDelay/nvidia-macos-driver-nvk/blob/main/docs/UPSTREAM-BACKPORTS.md), [hybrid doc](https://github.com/HighDelay/nvidia-macos-driver-nvk/blob/main/docs/HYBRID-LAPTOPS.md)). Untested on hardware by the author. Confidence: Low.

## Panel brightness after restart

- **An HP OMEN 16 (Ryzen 9, RTX 5070 Laptop) runs 3.1 with `nvrmacpibl=1` and gets hardware backlight, but the driver does not remember the level.** It starts at 100 percent after every boot. The author's fix is two launch items: a daemon that writes the `linear-brightness` display parameter before login, and a small watcher that calls the private DisplayServices call after login so the slider follows, and re-applies for 5 seconds after wake because the driver resets the panel again. He found that the `brightness` parameter is a placeholder and only `linear-brightness` moves the panel. He also says upstream PR #312 does not work on his machine ([README, section 3](https://github.com/Game-5040/hackintosh-hp-8f06-macos26/blob/main/README.md)). MIT licence. Why it matters: it matches our brightness-after-restart problem (I-137) and gives a userland workaround that needs no kernel change. Confidence: Medium, one machine, a working claim from the owner.
- HighDelay's fork adds `nvfbedpbl=1` (DPCD brightness over AUX on a panel with no NVKMS control) and a brightness helper that saves levels when firmware drops the NVRAM value ([backports](https://github.com/HighDelay/nvidia-macos-driver-nvk/blob/main/docs/UPSTREAM-BACKPORTS.md), commit [e419a973](https://github.com/HighDelay/nvidia-macos-driver-nvk/commit/e419a973)). Our laptop panel is wired to the iGPU in Hybrid, so this only matters in dGPU-only mode. Confidence: Low.

## Window drags and the shader cache stall

- **thanhnndev's fork (an ASUS G14 with a Radeon 890M panel and RTX 5060) spent the week on WindowServer cost in the Metal plugin.** A disk cache for the SPIR-V address lowering took 18 lowerings (about 1.2 s) to zero on a warm run ([0f2a94a5](https://github.com/thanhnndev/nvidia-macos-driver/commit/0f2a94a5)). Mapping the 153 MB QuartzCore metallib instead of copying it cut WindowServer's dirty heap by about 153 MB ([23af58ce](https://github.com/thanhnndev/nvidia-macos-driver/commit/23af58ce)). One fewer IOSurface call per present ([a1d784ee](https://github.com/thanhnndev/nvidia-macos-driver/commit/a1d784ee)). A default-off "flip census" shows who drives WindowServer's presents ([9d322f98](https://github.com/thanhnndev/nvidia-macos-driver/commit/9d322f98)). The author states the plugin is shared with the NVIDIA path, but the measurements are on his own test program, not on a desktop drag. Why it matters: these are cheap-to-check ideas for I-069 (shader cache stall after login) and I-136 (slow drags). The flip census idea is a way to find out what WindowServer is drawing. Confidence: Low to Medium for the numbers, they are the author's. Almost all commits are AI-written and single-laptop by the author's own warning ([release notes](https://github.com/thanhnndev/nvidia-macos-driver/releases/tag/ga403wm-890m-plugin-a6cec1b)). No licence asserted, ideas only.
- HighDelay's fork says "Keep unsynchronized rendering moving when drawables are busy" and fixes a 2x refresh-rate cap on Zink and native Vulkan ([0be2bfe8](https://github.com/HighDelay/nvidia-macos-driver-nvk/commit/0be2bfe8)). That is a Vulkan presentation path, not WindowServer. Not relevant to drags. Confidence: Low.
- A Turing PR on 1401 patches the framebuffer's 256 MB VRAM grant ceiling and turns off surface eviction after 100 ms to cure drag stutter on a small BAR1 ([1401 #179](https://github.com/nullmoth/1401/issues/179)). It patches binary offsets and was written for an RTX 2060 SUPER. Not our card, and our BAR is large. No action.

## Arrow Lake-HX and E-cores

- **A Core Ultra 7 251HX laptop (18 cores, RTX 5060 Laptop) cannot boot macOS 15.6 with the E-cores on.** It panics with `Should have 18 Cores, but only found 17 for Die 0` or `mp_rv_action entry: 3 of 4 responses`. With the E-cores off in BIOS it boots. The reporter's analysis of the XNU topology code says the CPUID and ACPI tables look consistent and the fault is in bring-up of one application processor. It is still open, with no maintainer answer ([1401 #190](https://github.com/nullmoth/1401/issues/190)). The 1401 recipe for the known 128-logical-per-package freeze (a Raptor Lake-P laptop) is already applied here, so it is not that bug ([recipes](https://github.com/nullmoth/1401/blob/main/p1401/machine_recipes.json)). An InsanelyMac reply on a different thread says recent OpenCore makes `ProvideCurrentCpuInfo` handle Arrow Lake without CpuTopologyRebuild ([thread](https://www.insanelymac.com/forum/topic/362692-unable-to-boot-into-macos-tahoe-with-core-ultra-arrow-lake/)). The date of that reply was not shown, so I cannot tell if it falls in the window. Why it matters: same CPU family as ours. Confidence: Medium for the report, Low for the OpenCore claim.

## NVIDIA open modules

- **620.70.10 (2026-11-23) is not newer than 620.73.04.** It is a single commit on the 620.70 datacenter branch (release notes link to the Tesla notes). Compared with 620.70.06 it touches UVM access-counter thresholds, SM debugger sessions and memory descriptors. Nothing on display, HDMI, suspend, GSP firmware or RTX 50 laptops ([release](https://github.com/NVIDIA/open-gpu-kernel-modules/releases/tag/620.70.10), [compare](https://github.com/NVIDIA/open-gpu-kernel-modules/compare/620.70.06...620.70.10)). No change to our pin. Confidence: High. MIT and GPL dual licence.

## Sensors

- **SMCNvidiaGPU 2.3 binds NullMoth 3.1 and adds a fallback table for 12 driver builds** ([release](https://github.com/zzzyy678/SMCNvidiaGPU/releases/tag/v2.3)). The author says 3.1 adds no new sensor channels: only GPU and memory temperature are valid and power is the module total. The fan RPM comes from the RUSD block. A Legion R9000P 3060 Laptop report was traced to a field-offset shift from 2.8 on and fixed in 2.3 ([#2](https://github.com/zzzyy678/SMCNvidiaGPU/issues/2)). Why it matters: a way to read dGPU temperature and fan RPM in macOS. Confidence: Medium. No licence asserted.
