# xe: 2026-11-21 to 2026-11-26

Read from GitHub only. Nothing below is reproduced on our machine.

- **A third Arrow Lake-H laptop has an accelerated desktop on our 0.0.48 kernel driver, and it ships a fix for the blur and ghosting faults.** The owner of a Motorola moto book 60 pro (Core Ultra 5 225H, Arc 130T `8086:7D51`, Sequoia 15.8.3) reports that WindowServer composites on the GPU, with transparency, blur, video wallpapers and zero-copy flips at about 40 to 45 fps while dragging windows ([README](https://github.com/sortedcord/MotoBook60Pro-Hackintosh-EFI/blob/main/README.md), [log](https://github.com/sortedcord/MotoBook60Pro-Hackintosh-EFI/blob/main/accel/LOG.md)). The userland is samwu07's ThinkBook Metal stack plus a patch against our a9dfe27 plugin. The patch changes `textureBarrier` in the Metal plugin. WindowServer calls it every frame for blur, and the old code only emitted a Vulkan barrier inside a live pass, so the snapshot it samples stayed stale. The new code ends the pass, copies the target into the snapshot, and resumes with load ([patch](https://github.com/sortedcord/MotoBook60Pro-Hackintosh-EFI/blob/main/accel/candidates/render-barrier-a9dfe278/render-barrier-only.patch)). Our plugin still has the one-line version, so this is a direct candidate for our ghosting and missing-element faults. The same log records a WindowServer stack overflow alternating `RenderEncoder` and `SetScissor`, and a display freeze during Safari video. The patch sits in the PolyForm Noncommercial plugin lineage, so we read it as a design and do not copy it. Confidence: Medium (owner's claim, one machine, userland is a third-party build).
- **HWP rescale and C-state findings give a second angle on I-116.** Two independent projects say XCPM mis-scales HWP requests on hybrid CPUs: one hybrid performance unit is about 78.7 MHz, XCPM writes 100 MHz units, so P-cores stop near 3.6 GHz. JulioNectar's XE-PM fixes this by routing the XCPM `wrmsr` site once, and also enables C8 and C10 in XCPM's idle table ([source](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/blob/main/src/NootedGreen/kern_xepm.cpp), [WhateverXe request](https://github.com/b00t0x/WhateverXe/issues/227)). kitsuneislife measured that turning HWP off in the CPUFriend board-id vectors lifted P-cores from 3.6 to 4.5 GHz, at 7.2 to 10.8 W idle ([commit](https://github.com/kitsuneislife/nmx-intel/commit/10bc4d2c)). Our LegionCpuPower already takes the highest ratio from HWP capabilities, so the scale problem is not ours. The point for I-116 is the method: a one-time hook at XCPM's write site could remove our 1 Hz cross-CPU rendezvous, which is our main suspect. Neither project ran on Arrow Lake, and neither declares a licence, so ideas only. Confidence: Medium for the mechanism, Unverified for any link to our stalls.
- **GuC SLPC sits at the efficient frequency under bursty compositing, and two projects raise the floor.** MeowXE3 1.0.13 asks for a 1500 MHz minimum through `xe_guc_pc_set_min_freq` once, after the first clock report. It measured frames waiting over 16 ms for the GPU fall from 5-17% to 1.5% ([commit](https://github.com/cuadra8998/MeowXE3/commit/56da9cf1)). ArrowWhatever, which targets the 275HX, raises the SLPC minimum when a frame is late and drops it 150 ms later ([README](https://github.com/Mountainatic/ArrowWhatever)). Neither says anything about GT C6 or stalls. It matters to us as a way to keep the GT out of low states during compositing, and as something to rule out while we chase I-116. MeowXE3 was PolyForm Noncommercial in the earlier README (GitHub now shows no licence), ArrowWhatever has none, so ideas only. Confidence: Medium (their own measurements, one machine each).
- **ArrowWhatever answered how it lights the panel before WindowServer.** Its maintainer says a separate `XeGfxDisplay.kext` subclasses `IOFramebuffer` directly (modes, pixel information, mapping, vsync, dependent ID set before `start()`), and i915 sets eDP link, mode and primary plane during kernel init ([reply](https://github.com/Mountainatic/ArrowWhatever/issues/3)). The README of this 275HX project also claims 1920x1200 HiDPI at 240 Hz over two pipes with DSC, hardware cursor, i915 backlight and a hardware gamma path. No code was read in this run, there are no commits since 2026-11-06, and no licence is stated. Confidence: Low (README claim only).
- **WhateverXe 0.8.4 and 0.8.5 touch our display questions.** 0.8.5 keeps the firmware CMTG on the internal eDP handoff and retraining ([commit](https://github.com/b00t0x/WhateverXe/commit/bb7fad97)). 0.8.4 fixes a framebuffer allocation that ended mid-page on 2880x1800 panels, a panel keeping DSC enabled when switching to an uncompressed link, and a kernel panic when the video-engine interrupt identity does not arrive; the last one comes with a model of the shared bank-1 identity latch between VCS and VECS ([0.8.4](https://github.com/b00t0x/WhateverXe/releases/tag/0.8.4), [0.8.5](https://github.com/b00t0x/WhateverXe/releases/tag/0.8.5)). It is Tiger, Alder and Raptor Lake on Apple's driver, so none of it applies as code. The DSC and mid-page items are worth checking against our own eDP path. BSD-3-Clause. Confidence: High for what changed, Low for relevance.
- **A Panther Lake machine now renders Metal frames through a private device.** lemlnn's Framework 13 Pro (B082, Sequoia) shows 12 changing frames in a CAMetalLayer window, 2 GiB of randomised async work, and a working IOSurface host import. The import failed at first because `xe_hmm_userptr_populate_range` was a stub returning -45, so he wrote the page-pin, scatter-gather and DMA path, limited to 64 pages per import and 16 mappings ([findings](https://github.com/lems-hardware/lhl-hackintosh-docs/blob/main/TECHNICAL-FINDINGS.md), [evidence](https://github.com/lems-hardware/lhl-hackintosh-docs/blob/main/logs/graphics-evidence.md)). Our IOSurface gap may need the same import path. Ordinary Metal discovery and accelerated WindowServer are still unverified there. CC-BY-4.0 for the docs. Confidence: Medium.
- **Hardware cursor gate: a fourth machine.** The moto book keeps its boot framebuffer at GGTT `0xFF600000`, not the `0xff000000` our cursor check expects ([log](https://github.com/sortedcord/MotoBook60Pro-Hackintosh-EFI/blob/main/accel/LOG.md)). With #19 and #21 that makes four machines. Confidence: Medium (the log gives the GGTT range, not a cursor result).
- **Small items.** zep245's last build of the old driver lets Brave's GPU process use the Metal plugin: it recognises the new helper name and no longer treats a sandbox-blocked "armed" check as "not armed" ([v1.3.0](https://github.com/zep245/IrisXe-macos-driver/releases/tag/v1.3.0)); we should check our plugin does the same. WhateverXe Graphics 0.4.5 stops failed video RGB conversions being shown as valid frames ([release](https://github.com/b00t0x/WhateverXe-Graphics/releases/tag/v0.4.5)). A hybrid-laptop project found its HDMI port is wired to the RTX, so a hotplugged display stays dark on the iGPU path ([note](https://github.com/kitsuneislife/nmx-intel/commit/386a6abb)); worth confirming on the Legion before we plan external displays.

Skipped: WhateverXe issue traffic on Tiger, Alder and Raptor Lake, NootedGreen reports, metal2vulkan (Linux-hosted Metal translator, no macOS driver), drm-kmod threads about Linux 6.15 and GPL handling, and EFI-only discovery hits.
