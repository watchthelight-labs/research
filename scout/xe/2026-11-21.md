# xe: 2026-11-13 to 2026-11-21

Read from GitHub only. Nothing below is reproduced on our machine.

- **A Panther Lake laptop reached stages 1 to 6 on a core from our lineage, and found a locking trap that our shim may share.** lemlnn's Framework Laptop 13 Pro (Arc B390, `8086:B082`, macOS 15.8.3) runs a patched build that comes from InSnh-Gd's fork of our 0.0.47 with Mubai's Panther Lake changes. His log has GuC 70.72.1 running on both GTs, six engines completing batches, and a user-space submit whose GPU write was read back by the CPU. No accelerator and nothing drawn yet ([write-up](https://github.com/lems-hardware/lhl-hackintosh-docs/blob/main/TECHNICAL-FINDINGS.md), reported in [#11](https://github.com/watchthelight-labs/WTLIntelGfx/issues/11)). The find is in attempts 119 and 120: the compatibility layer treated SRCU as plain RCU, plain RCU readers run with preemption off, and `drm_dev_enter` holds its SRCU lock across a blocking fence wait, so the kernel panicked about two seconds into stage 4. His fix gives only the DRM domain a sleepable SRCU. It is described in prose, the patch is not public. Our own shim pins RCU readers inside a critical section (see `xg_sched_pin` in [xg_sched.c](https://github.com/watchthelight-labs/WTLIntelGfx/blob/main/shim/src/fbsd/xg_sched.c)), so the same question applies to us: does any SRCU reader sleep? Not checked yet, because the LinuxKPI sources are on the machine we cannot boot right now. Confidence: Medium-High for his log, Unverified for our tree.
- **yusufklncc's Arc B580 driver found an ANV bug that drops a layer from app icons, with a test.** With descriptor buffers, a set offset given for an empty set layout marks no shader stage, so ANV does not reload its offset table and a later layout at the same slot reads a stale offset. The visible result was layered icons with a layer missing, different on each launch. Fixed in their plugin and as a Mesa patch with a test that fails without it ([0.1.7](https://github.com/yusufklncc/intel-gpu-macos-driver/releases/tag/v0.1.7)). We run the same plugin family on ANV and have open drawing faults (I-119), so this is a candidate cause to test. The same release fixes a shutdown panic (`complete() while dma active`, a kept DMA mapping without a wire), stops reading the composite back every frame (97.6 to 175.9 fps at 4096x2304 on their machine), raises the GuC clock floor for 400 ms on the first frame after idle, and cuts framebuffer-fetch barriers from about 300k to under 10k per second. One desktop with a discrete card, their numbers. GitHub does not recognise the licence, so ideas only until we have read it. Confidence: High for the ANV analysis, Medium for the numbers.
- **The ThinkPad E16 owner tried the real `xe` driver on Arrow Lake-H and went back to our stack.** MeowXE3 forced onto `7D51` showed a desktop once, then froze the whole machine one to two minutes into every boot, with no panic and no log, under bursts of GPU work. Turning PSR, FBC and DC5/DC6 off did not stop it. He parked it on 2026-11-22 and returned to XeGfx ([handoff](https://github.com/taqieallah/ThinkPad-E16-ArrowLake-macOS/blob/main/HANDOFF.md)). So the `xe` route for [#8](https://github.com/watchthelight-labs/WTLIntelGfx/issues/8) is not a drop-in on Arrow Lake. Cause unknown. Confidence: Medium.
- **A second Arrow Lake-H user reports that the panics stop with the HWP part of LegionCpuPower off.** ChariskRichy (ThinkBook 16 G7+, Core Ultra 5 225H, `7D51`, macOS 26.6) has an accelerated desktop on 0.0.47 and says the freeze and panic came back with the fan part off but stayed away with HWP off ([comment](https://github.com/taqieallah/ThinkPad-E16-ArrowLake-macOS/issues/1#issuecomment-7070646624)). That agrees with our suspect for I-116. No panic file is posted yet, so we do not know that it is the same panic. Confidence: Low until the log arrives.
- **FreeBSD drm-kmod now clears the GGTT when i915 unloads.** Entries kept pointing at freed pages, so after an unload the GPU could write into memory that had been reused ([PR 531](https://github.com/freebsd/drm-kmod/pull/531), merged 2026-11-18). Our i915 comes from this tree and we unload and restart it during tests. Small and worth porting. The shmem data-loss report next to it ([#527](https://github.com/freebsd/drm-kmod/issues/527)) is about FreeBSD's pager and its repro is GPL, so we leave it. Confidence: High for the mechanism.
- **WhateverXe 0.8.3 adds brightness over the eDP AUX channel.** A 47-line header reads the DPCD backlight capabilities and writes mode, level and enable ([0.8.3](https://github.com/b00t0x/WhateverXe/releases/tag/0.8.3)). The author says it is not yet validated on a panel. It is BSD-3. For our missing Intel-panel brightness (I-137) the first step is to read our panel's DPCD 0x700 to 0x702 and see whether it supports AUX control at all. Confidence: Medium.
- **New: MeowXE3, the Linux `xe` driver on NullMoth's LinuxKPI.** Its README reports Metal, Vulkan and a GPU-composited desktop on one Wildcat Lake Vivobook (`8086:FD80`), and says the Panther Lake IDs in it never ran on hardware ([repo](https://github.com/cuadra8998/MeowXE3)). PolyForm Noncommercial, so ideas only. It is the best evidence so far that the `xe` route works on one Xe3 machine. Confidence: Medium, README claims.
- **New: Mubai's Panther Lake logs** ([repo](https://github.com/yangyishuo1124/Mubai-s-Hackintosh-Logs)) carry a copy of our tree with their changes. Their own record lists what is verified (stages 1 to 3, a Metal compute test, display takeover at 2560x1600) and what is not (WindowServer on the desktop). GPL-3.0.
- **New, small: a CI build of the E16 console-range kext** that follows our build script and credits us ([repo](https://github.com/RUI-JACK/e16-consolerange-build)). Untested by its builder.
