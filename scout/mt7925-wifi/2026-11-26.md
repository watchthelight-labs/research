# mt7925-wifi: 2026-11-21 to 2026-11-26

Read from GitHub. Nothing below is reproduced on our machine.

- **Linux mt76 had 33 commits in the window. None touches channel switch, roaming, beacon loss, suspend or firmware load for a single-link station.** So I-139 (link drops on an AP channel switch) and I-140 (no roaming) get nothing new from upstream this week. Fifteen of them are on [master](https://github.com/openwrt/mt76/commits/master) and eighteen on its `pending` branch, which is not merged. I also read the MCU core series of 24 November on master. Most of them are MLO, AP MLD, monitor mode and mt7996 fixes that do not reach a station on one link. mt76 is ISC licensed and we port from it. Confidence: High, read from the diffs.
- **The 5.9 GHz channel list for the per-rate power limits is missing in our port.** mt76 added channels 163, 169, 173, 175 and 177 to the 5 GHz list that `mt7925_mcu_rate_txpower_band` sends ([99265f9a](https://github.com/openwrt/mt76/commit/99265f9a)). Our `ratePowerBand` still ends at 167. The last-batch size bug fixed in the same commit does not exist in our loop. Why it matters: channels above 165 get no per-rate limit from us, which probably leaves the firmware default. Affects regions that allow 5.9 GHz. Confidence: High for the diff, Unverified for the effect.
- **We never read the firmware status of a command.** Since 23 November mt76 logs the command, sequence number and status when the firmware answers with an error ([bc394ec4](https://github.com/openwrt/mt76/commit/bc394ec4)). Our `uniCmd` returns success as soon as the event with the right sequence number arrives, and almost every caller passes no event buffer, so a rejected BSS, station or ROC command looks like a success. Worth adding a status check and a log line first, then deciding what to do about a refusal. Confidence: High from our source.
- **mt76 now retries only read commands and fails commands during an MCU reset.** A command whose answer is lost may have run, and running it twice can clear the wrong station ([d33e3f3e](https://github.com/openwrt/mt76/commit/d33e3f3e), [07a4dccd](https://github.com/openwrt/mt76/commit/07a4dccd), [7dbec475](https://github.com/openwrt/mt76/commit/7dbec475)). We do not retry at all and we mark the firmware dead after three timeouts, so we are on the safe side. After our chip reset and reload we rejoin from scratch, which also avoids the unknown-state problem. All three are on master. Confidence: High.
- **Group key replay counters: same shape as an mt76 bug.** mt76 found that one counter set for all group keys makes frames of a new key read as replays when one frame of the old key arrives during a rekey, and chose to skip the check ([339bbc19](https://github.com/openwrt/mt76/commit/339bbc19), [a2da88c8](https://github.com/openwrt/mt76/commit/a2da88c8), `pending`). Our counters are one set per TID for the group key, reset to the Key RSC at install (`pnAccept`). A late frame of the old key after a rekey could raise the counter and drop good frames for a while. The window is small. Not seen on hardware. Confidence: Low to Medium. The thanhnndev notes also show an AP that rekeys its group key every 30 to 80 s ([section 10.44](https://github.com/thanhnndev/mt7925-macos/blob/main/docs/ROADMAP-AWDL.md)), which makes the case easy to trigger. Test: rekey every minute and count `pnreplay`.
- **Checked and not affected.** Replay checks for group management frames (BIP, [07b4f2b7](https://github.com/openwrt/mt76/commit/07b4f2b7)): we offer no PMF. Translated frames that were not decrypted ([4c6fbc33](https://github.com/openwrt/mt76/commit/4c6fbc33)): we drop translated frames on a protected link. USB probe reset ([e191a600](https://github.com/openwrt/mt76/commit/e191a600)): USB Wi-Fi only; we use PCIe. EHT, LDPC and HE capability fixes: AP or MLD only.
- **Worth keeping for later.** MT7928 drops host MMIO writes to the WTBLON registers, so mt76 programs the fixed rate table through the MCU register command there ([956bb3cd](https://github.com/openwrt/mt76/commit/956bb3cd)). We write that table by MMIO. Keep this in mind when we build the MT7927 backend. The WoWLAN resume fix resets the group replay counters because the firmware may renew the GTK while the host sleeps ([a5589959](https://github.com/openwrt/mt76/commit/a5589959), `pending`). Relevant once we offload rekey for sleep. Confidence: High for the diffs.
- **AirportMtkWlan v2.2.3 "warm boot stability" is a Wi-Fi attach fix on MT7921 and MT7922, and we already do the same thing.** It forces fw-own then drv-own at attach when the host already owns the chip, because a warm boot left the firmware asleep ([diff](https://github.com/Arxusion/AirportMtkWlan/compare/v2.2.2...v2.2.3)). Our attach always runs `fwOwn` then `drvOwn`, with 10 tries of 50 ms. The release also fixes a TX cleanup race that double-freed mbufs. Our TX cleanup path was not checked against it. The release note says AWDL is now safe to enable, but four reports in [issue 24](https://github.com/Arxusion/AirportMtkWlan/issues/24) and [issue 23](https://github.com/Arxusion/AirportMtkWlan/issues/23) say it still freezes boot. GPL-3.0, ideas only. Confidence: High for what the diff does.
- **[seaurching/mt76wm](https://github.com/seaurching/mt76wm) is a new MT7921 and MT7922 kext, GPL-2.0, on an itlwm base, from 6 November.** It shares no code with us. Its commit messages list bugs a PCIe mt76 port on macOS can hit. Delivering RX frames while holding a spin lock panicked the kernel, and sizing an mbuf with its current length dropped every frame ([c761de40](https://github.com/seaurching/mt76wm/commit/c761de40)). Our RX path copies into an mbuf from the front end allocator and does not do either, from reading `deliver`. It also says arming the MCU-to-host interrupt before the WFSYS reset fixed a dead semaphore ([373640e6](https://github.com/seaurching/mt76wm/commit/373640e6)). We arm it after the reset and our firmware loads, so this may be MT7921 only. Last, it blames the firmware for hiding beacons in BSS mode, which kept the join from latching ([e5af3447](https://github.com/seaurching/mt76wm/commit/e5af3447)). That is a claim on another chip. We do see beacons while associated, but whether they all arrive (I-139) is still open. Joins there still fail. Confidence: Low for relevance, High for what the commits say.
- **ForbiddenItlwm 0.7.0 alphas and RTL8814Native** are Intel and Realtek AWDL work. They matter for the native front end, see the other write-up. One Wi-Fi point: [ForbiddenItlwm](https://github.com/retropineaple/ForbiddenItlwm/commit/3230f239) fixed hidden networks by putting the name into the probe request of a directed scan. GPL-2.0, ideas only. Worth a check that our directed scan does the same.
- **More machines run our kexts, and sleep is still open.** The Y7000P owner now says sleep "seems to have some problem", with possible spurious wakes ([Cube-geometric commit](https://github.com/Cube-geometric/Hackintosh-Legion-Y7000P-IRX10-EFI-with-MT7925-and-Trackpad/commit/60063423)). The ThinkBook owner corrected his README: his BIOS has only S0ix, so the earlier "sleep works" was display sleep and DarkWake ([commit](https://github.com/Yangcheng811/ThinkBook-16p-2025-G6-ADR-Hackintosh/commit/eefbb9d0)). The HP owner moved to WTLWireless 0.15.0 ([commit](https://github.com/Game-5040/hackintosh-hp-8f06-macos26/commit/b4133073)). User reports. We still handle no real sleep.

Skipped: MT7902 repos ([minhvmware](https://github.com/minhvmware/mtk-macos-driver), [jacksproject](https://github.com/jacksproject/MT7902-WiFi-Kext)) other chip, no relation to us found; Intel, Realtek and EFI-only repos.

Next on our side: add the status check to `uniCmd`, add the 5.9 GHz channels, and test the group rekey case before touching sleep.
